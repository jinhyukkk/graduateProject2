## 국문초록

비전공 실무자가 자연어로 사내 관계형 데이터베이스에 접근할 수 있다면, 사전 화면 개발 없이 데이터 활용 병목을 제거할 수 있다. 다만 안전한 운영을 위해서는 *실행에 성공한 쿼리가 사용자 의도와 일치하는지*를 별도로 보장해야 한다. 기존 자기교정 연구는 실행 가능성과 결과 동치성 등 *코드와 실행* 측면에 집중되어 의미 차원의 미탐지 영역을 포착하기 어렵다. 본 연구는 (i) 자연어 역번역과 자연어 추론(NLI)을 결합한 **의도 정합성 검증기**, (ii) 오류 유형별 **분기 교정기**, (iii) 한국형 인사 도메인의 네 가지 특수성(영문 컬럼명, 코드/명칭 페어, 이력 테이블 시점, 시간 표현 cut-off)에 대응하는 **도메인 적응**, (iv) 응답 다양성을 활용하는 **Self-Consistency 후보 생성(k=5)**, (v) 이들을 단일 파이프라인으로 결합한 **자기교정 Text-to-SQL 시스템**을 제안한다. 평가는 BIRD dev_300(n=300)과 인사 도메인 합성 평가셋(n=257; 수동 시드 30개 + 자동 검증 227개, 5 페르소나 × 3 난이도)에서 수행한다. DAIL-SQL, MAC-SQL, zero-shot 베이스라인은 동일한 GPT-4o 백본으로 재실행하여 공정 비교하며, DIN-SQL 재실행은 향후 측정으로 남긴다. 본 연구의 절대 실행 정확도(EX) 목표는 BIRD 리더보드 1위(2026-04 기준 77.64%, GPT-4o 백본) 추격이 아니라, *동일 백본 환경에서 최첨단(SOTA) 기법이 다루지 않은 한국어 기업 인사 도메인에 대한 응용 시스템과 운영 가이드라인 제시*이다. 핵심 정량 결과는 두 가지다. 첫째, NLI 기반 교정 트리거의 *전역 EX 기여*는 고성능 LLM 환경에서 통계적으로 유의하지 않다(연구 질문 1의 가설을 약하게 부정한다). 둘째, *보조 관찰 지표*인 **단독 탐지율**—실행 검증을 통과한 *실행 통과 오답 영역*(EX=0, 외부 BIRD gold 기준)에서 NLI가 단독으로 탐지한 비율—이 본 BIRD dev_300 표본에서 68.1%(98/144)로 관측된다. 이 결과는 NLI를 *교정 트리거*가 아닌 **독립 진단 축**으로 운영하는 패턴을 본 표본 규모에서 지지한다(통계적 일반화 한계는 §6.4 참조). 본 연구는 이 비대칭 결과를 단순한 EX 미달성으로 해석하지 않고 **검증 축의 역할 분리에 대한 운영 가이드라인**으로 정리하며, NLI 점수, SQL 신뢰도, 실행 결과 상태의 결합 조건에 따른 단계별 운영 표를 제시한다. 의미 검증 도입, 유형별 분기 교정, 한국어 도메인 적응, 운영 가이드라인 도출이라는 네 계층 기여는 *비전공 실무자가 자연어만으로 별도 화면 개발 없이 기업 데이터에 접근*하는 응용 목표를 일관된 흐름으로 연결한다(Self-Consistency 후보 생성 k=5는 외부 검증 기법의 차용으로 별도 기여로 계상하지 않는다).

**주제어**: Text-to-SQL, 자기교정 시스템, 의도 정합성 검증, 자연어 추론(NLI), 한국어 인사 도메인, 운영 가이드라인, 비전공자 데이터 접근

## 제1장 서론

### 1.1 연구 배경 및 동기

#### 1.1.1 한국 IT 서비스 산업의 데이터 활용 병목

한국 기업의 디지털 전환이 가속화되면서 사내 데이터의 즉시 조회·분석 수요는 빠르게 늘고 있다. 그러나 인사·재무·운영 등 핵심 업무 데이터는 대부분 관계형 데이터베이스(이하 관계형 DB)에 저장되어 있고, 이를 활용하기 위해서는 구조적 질의 언어(SQL) 작성이 필요하다. 현업 실무자 대부분은 SQL 전문가가 아니므로, 단순한 조회 한 건을 위해서도 데이터 분석 조직 또는 IT 부서에 의존해야 하는 병목이 상존한다. 이를 우회하기 위해 한국 기업은 통상적으로 **현업 요구마다 별도의 조회 화면·리포트·비즈니스 인텔리전스(BI) 대시보드를 신규 개발**해 왔다. 이러한 사전 개발 방식은 다음 세 가지 구조적 한계를 가진다.

- **(i) 요구사항 변경 둔감성** — 한 화면 개발에 평균 수 주~수 개월이 소요되어, 요구사항이 진화하는 속도를 따라잡지 못한다.
- **(ii) 비용 누적** — 신규 질의 한 건당 *화면, 응용 프로그래밍 인터페이스(API), 권한 설계*가 추가되어 운영 비용이 선형적으로 증가한다.
- **(iii) 임의 질의의 원천 봉쇄** — 사전에 정의되지 않은 임시(ad-hoc) 질의가 *기술적으로 불가능*해져, 데이터 기반 의사결정의 잠재력이 구조적으로 제약된다.

이 병목은 *데이터 분석 인력 부족과 SQL 전문성 편중*이 지적되는 한국 IT 서비스 산업 환경에서 특히 심각하다. 인사·재무·운영처럼 *열 단위 의미가 조직별로 달라지는* 도메인에서는 IT 부서조차 사용자 의도를 정확히 해석하기 어려우며, 그 결과 의사결정 지연과 데이터 활용도 저하가 동시에 발생한다.

#### 1.1.2 자연어 인터페이스의 가능성과 운영 위험

본 연구의 출발점은 이 병목을 **사전 개발이 아닌 자연어 질의(Natural Language Query)로 해결**하는 데 있다. 비전공 실무자가 사내 관계형 DB에 한국어로 묻고 결과를 즉시 받을 수 있다면, 신규 화면 개발 없이 임의 질의가 가능해지고 데이터 활용 병목이 크게 완화된다. 그러나 자연어 인터페이스의 도입에는 *운영적 위험*이 동반된다.

**위험 ①: 의도 불일치 오류.** 쿼리가 구문상 문제없이 실행되어 결과 행을 반환하더라도, 그것이 사용자의 *의도* 와 부합한다는 보장은 없다. 예를 들어 "작년에 퇴사한 직원 중 기술직 인원수" 라는 질의에 대해 LLM이 `WHERE year = 2025`로 작성할 경우, 현재가 2026년이면 "작년"은 2025년이 맞지만 기업의 회계연도 정의에 따라 결과가 달라질 수 있다. **문법적으로 유효하고 실행 또한 성공하는 쿼리가 의미적으로 잘못** 된 경우, 기존의 실행 기반 검증만으로는 오류를 포착할 수 없다.

**위험 ②: 한국형 도메인 특수성.** 한국 기업의 사내 시스템 중 인사·재무 등 *레거시 운영 기간이 긴 도메인*에서는 (a) 8자 이내 영문 약어 컬럼명(`THRM151`, `JIKGUB_CD` 등 — 일부 환경), (b) 코드 컬럼과 명칭 컬럼의 페어링(`*_CD`/`*_NM`), (c) 시작일·종료일 기반 이력 테이블, (d) 회계연도·반기 등 시간 표현의 회사별 정의 라는 네 가지 구조적 특수성이 자주 관찰된다. 이 비대칭은 *공개 영어 벤치마크에는 거의 등장하지 않는* 한국 특유의 도전이며, 단순 LLM 호출로는 안정적으로 처리되지 않는다.

**위험 ③: 자동화 vs 안전성의 트레이드오프.** 50% 정확도의 시스템을 *완전 자동* 으로 운영하면 절반의 결과가 잘못된다. *모두 사람이 검토* 하면 자동화의 의미가 사라진다. 따라서 *어떤 쿼리는 자동 실행하고, 어떤 쿼리는 사람 검토를 권하며, 어떤 쿼리는 다시 만들지* 를 판단하는 **운영 정책** 이 시스템 도입의 핵심 결정 요소가 된다.

#### 1.1.3 본 연구의 응용 목표와 검증 사례

위 세 위험을 동시에 다룰 수 있는 **전 과정(end-to-end) 응용 시스템**의 설계와 검증이 본 연구의 상위 목표이다. 본 연구는 (i) 한국형 인사 도메인의 네 가지 특수성에 강건한 SQL 생성, (ii) 의도 불일치 오류를 *실행 검증과 독립적으로* 진단하는 의미 검증, (iii) 정확도 한계 환경에서의 *증거 기반 운영 가이드라인* 도출을 핵심 결정으로 하여, 비전공 실무자가 *서비스 형태로 직접 사용 가능한* 자기교정 Text-to-SQL 시스템을 제시한다.

검증을 위한 **응용 사례**로 본 연구는 기업 인사 데이터베이스(HRDB)를 선택한다. 인사 도메인은 (a) 대부분의 한국 기업이 보유하고 있어 일반화 가능성이 높고, (b) 직급·직책·근속·보상 등 *조직별 정의가 다른* 컬럼이 다수 존재해 자연어→SQL 변환의 도전을 잘 드러내며, (c) 개인정보 제약으로 외부 평가 데이터 확보가 어려워 본 연구가 함께 제안하는 *스키마-온리 평가 프로토콜*의 가치가 분명하기 때문이다. 따라서 인사 도메인은 본 연구의 핵심 적용 사례이자 *한국 산업 환경의 대표 사례*로 자리매김한다.

Text-to-SQL은 자연어 질의를 SQL로 변환함으로써 이 병목을 해소하려는 연구 분야이며, 최근 대규모 언어모델(Large Language Model, LLM)의 등장과 함께 정확도가 빠르게 향상되었다. 대표적으로 BIRD 벤치마크[^1] 검증셋에서 GPT-4 기반 기법은 60%를 상회하는 실행 정확도(Execution Accuracy, EX)를 보고하며[^1][^2], 이는 2년 전 수준(40% 이하)과 비교해 큰 진전이다. 그러나 여전히 **30% 이상의 질의에서 오류가 발생**하며, 실무 도입 관점에서 더 심각한 문제는 *오류의 성격*이다. 쿼리가 구문상 문제없이 실행되어 일부 행을 반환하더라도, 그것이 사용자의 *의도*와 부합한다는 보장은 없다. 예를 들어 "작년에 퇴사한 직원 중 기술직 인원수"라는 질의에 대해 LLM이 `WHERE year = 2025`로 작성할 경우, 현재가 2026년이면 "작년"은 2025년이 맞지만 기업의 회계연도 정의에 따라 결과가 달라질 수 있다. 이처럼 **문법적으로 유효하고 실행 또한 성공하는 쿼리가 의미적으로 잘못**된 경우, 기존의 실행 기반 검증만으로는 오류를 포착할 수 없다.

이 문제를 해결하기 위해 최근 **자기교정(self-correction)** 기법이 활발히 제안되어 왔다. DIN-SQL[^4]은 난이도 기반 분해와 자기 교정 프롬프트를, MAC-SQL[^5]은 세 에이전트(선택자·분해자·정제자)의 협업을, DAIL-SQL[^2]은 구조·의미 유사도에 기반한 few-shot 선택을 제안하였다. 또한 SQLFixAgent[^6]와 MAGIC[^7] 등은 실행 결과를 재분석해 교정 루프를 수행하는 방법을 제시한다. 그러나 이들 접근은 공통적으로 **(i) 실행 가능성과 결과 동치성 중심의 검증 축**에 머무르며, **(ii) 교정 단계에서 오류 유형을 식별하더라도 동일한 공용 프롬프트로 일괄 수정**하는 경향이 있다. 그 결과 "실행은 되지만 의도가 다르다"는 유형의 오류는 여전히 실행 통과 오답 영역으로 남는다.

### 1.2 연구 문제 정의

본 연구는 위에서 식별한 응용 격차를 해소하기 위해, *시스템* 차원과 *방법론* 차원의 문제를 동시에 다룬다.

**[상위 시스템 문제]** 비전공 실무자가 사내 관계형 DB에 자연어로 묻고 결과를 *즉시·안전하게* 받기 위해 어떤 구성 요소가 필요한가? 이는 단일 LLM 호출로 해결되지 않으며, (i) 한국형 도메인 스키마(영문 약어 컬럼명, 코드/명칭 페어, 이력 테이블)에 강건한 SQL 생성, (ii) 잘못된 결과를 자동 진단·경고하는 안전망, (iii) 비전공 사용자가 추론 과정을 추적할 수 있는 가시화, (iv) 개인정보 제약 하의 사전 검증이 모두 결합되어야 한다.

**[방법론적 하위 문제]** 위 시스템을 구성하는 핵심 결정 두 가지를 정량 검증한다.

- **연구 질문 1(RQ1, 검증 축의 역할).** 생성 SQL을 자연어로 역번역해 자연어 추론(Natural Language Inference, NLI)으로 원 질의와의 의미 일치를 판정하는 방식은 기존 실행 기반 검증과 *어떤 관계*에 있는가? 두 축은 (a) *동일한* 오류 집합을 포착하는 중복 관계인가, (b) *교정 트리거*로서 EX를 추가 향상시키는가, 아니면 (c) 실행 축이 통과시키는 *실행 통과 오답 영역*을 *독립적으로 탐지*하는 보완 관계인가?
- **연구 질문 2(RQ2, 교정 축의 분기).** 진단된 오류 유형별로 *전용* 교정 지시문을 사용하는 방식은 단일 공용 교정기 대비 특히 의미·구조적 오류 유형에서 교정 정확도를 향상시키는가?

본 연구는 RQ1을 가부 판정이 아닌 **세 가설(중복/교정 기여/독립 탐지) 중 어느 모드가 GPT-4o급 백본 환경에서 성립하는가**로 정식화한다. 이 세 모드 분해는 사전 등록된 가설이 아니라 파일럿 관찰(§3.2) 이후 본 연구가 정식화한 *탐색적(exploratory) 분석*에 해당하며, 이를 통해 단일 RQ의 실패가 아닌 **검증 축 역할 분리에 대한 운영 가이드라인**(§6.2)의 근거를 도출한다. 세 모드의 정식화 시점, 진단 가설 임계값(단독 탐지율 ≥ 30%), 임계값 설정 근거는 §3.2의 각주에 git 기록으로 명시하며, 사전 등록 부재는 §6.4의 한계로 명시한다.

**[평가 인프라 문제]** 기업 실 데이터(특히 인사)는 개인정보 이슈로 외부 반출이 불가능한 경우가 많아 평가 재현성이 저하된다. 본 연구는 데이터 정의어(Data Definition Language, DDL) 구조와 외래키 관계만 이식하고 행은 합성하는 **스키마-온리 평가 프로토콜**을 제안해 이 제약을 우회한다.

**[최첨단(SOTA) 격차에 대한 자리매김]** 2026-04 기준 BIRD 공개 리더보드 상위 시스템(AskData + GPT-4o 77.64%[^14], Agentar-Scale-SQL 74.90%[^15], CHASE-SQL + Gemini 74.90%[^13] 등)은 본 연구와 동일한 GPT-4o 백본 또는 더 큰 자원을 사용하면서도 60~75%대의 EX를 보고한다. 본 연구의 절대 EX 목표는 이 리더보드 추격이 아니다. 상위 시스템이 채택한 핵심 기법(Self-Consistency, 추론 시 자원 확장(test-time scaling), 토너먼트 선택기, 강화학습(RL) 선호 모델)은 본 연구의 기여 축(NLI 의미 검증, 한국어 인사 도메인 적응, 응용 시스템, 운영 가이드라인)과 *독립적으로 작동*한다. 본 연구는 이 독립 기여를 명시하면서 상위 시스템에서 검증된 Self-Consistency(k=5)를 적용 가능한 한도 내에서 차용해 EX 격차를 줄이되, 핵심 기여를 EX 절대값이 아닌 **검증 축 분리 운영 패턴**으로 명확히 한다.

### 1.3 연구 기여

본 연구의 기여는 *응용 시스템 → 방법론 → 평가 인프라 → 운영 가이드라인*의 **네 계층 기여**로 구성되며(Self-Consistency k=5는 외부 검증 기법의 차용으로 별도 계상하지 않는다), 각 계층은 비전공 실무자의 기업 데이터 접근이라는 상위 목표를 향해 일관된 흐름으로 결합된다. 본 연구는 네 계층 기여 중 *측정 완료 약 1.5계층, 측정 예정 약 2.5계층*으로 정량 검증 범위가 비대칭이다. 이 비대칭은 본 연구 범위의 한정에서 도출된 사항이다(§6.4 한계 13 참조).

본 연구의 *정량 측정*이 완료된 1.5계층 영역은 (i) 기여 2의 단독 탐지율 보조 관찰(BIRD dev_300, 네 셀 분포 단일 시행), (ii) 기여 2·3의 어블레이션 4종(A0/A1/A3/A4, paired bootstrap 95% CI), (iii) 평가 인프라 항목 일부의 동일 백본 베이스라인 비교(BIRD dev_300, DAIL-SQL·MAC-SQL·zero-shot, DIN-SQL은 향후 측정)이다. *서술적·정성·향후 측정*의 약 2.5계층 영역은 (a) 기여 1 시연 시스템(§4.6)의 5 페르소나 사용성 검증(정성 36회 단일 시행), (b) 기여 3 한국형 도메인 적응 네 영역의 *사례 연구* 검증(HRDB 257건 중 수동 시드 30건만 정량, 자동 검증 227건은 향후 측정), (c) 기여 5 운영 가이드라인의 정성 의사결정 표(§6.2 표 10)로, 본 연구의 정량 결론에 *직접* 의존하지 않는 부분이다. 이 비대칭은 *기여 네 계층 계상 자체*의 정당성 문제라기보다는 *측정 완료 폭의 점진 확장*으로 후속 연구에서 보강될 영역이다(§6.4 한계 13 참조).

> **[6개 항목과 네 계층의 매핑]** 본 §1.3의 항목 1~6은 네 계층 기여를 세분 표기한 것이며, *별도 계상하지 않는 항목 4(Self-Consistency k=5 외부 차용 기법)*를 제외하면 항목 1, 항목 2·3, 항목 5, 항목 6이 각각 계층 1(응용 시스템), 계층 2(방법론), 계층 3(평가 인프라), 계층 4(운영 가이드라인)에 대응한다.

1. **[응용 시스템] 비전공 실무자의 기업 데이터 접근을 위한 전 과정(end-to-end) 자기교정 Text-to-SQL 시스템(SC-TSQL)** — 사내 관계형 DB를 별도 화면 개발 없이 자연어 질의로 조회·분석하도록 하는 통합 시스템을 제안한다. 시스템은 (a) 한국형 기업 도메인(영문 컬럼명, 코드/명칭 페어, 이력 테이블)에 강건한 스키마 링킹과 도메인 단서(evidence) 자동 주입, (b) 사전 확정(Pre-finalization) 체크리스트 기반 사고연쇄(CoT) 생성, (c) 실행 검증과 NLI 의미 검증의 병렬 실행, (d) 오류 유형별 분기 교정, (e) 결과의 자연어 설명을 단일 파이프라인으로 결합한다. 시연 시스템(§4.6)에서는 채팅형 인터페이스, 추론 과정의 토큰 단위 스트리밍, 페르소나 기반 예시 카드를 통해 비전공 사용자가 *서비스 형태로 직접 사용 가능*함을 보인다.

2. **[방법론] 의도 정합성 검증기(Intent Consistency Check, ICC)와 검증 축의 역할 분리 명세** — SQL을 자연어로 역번역한 뒤 NLI로 함의 관계를 판정하는 모듈을 설계하고, 이를 실행 기반 검증과 *병렬로* 배치해 실행 축이 포착하지 못하는 의도 불일치 오류를 독립적으로 탐지한다. 본 연구는 ICC를 EX의 보조 지표가 아니라 **(a) 교정 트리거 축과 (b) 독립 진단 축**의 *두 가지 역할*로 명시하고, 두 역할 각각의 기여를 어블레이션으로 분리 측정한다. 또한 실행 통과 오답 영역(실행 통과 + 오답)에서 NLI의 독립 탐지 비율을 *서술적 보조 관찰 지표인 **단독 탐지율***로 정의해, 실행 정확도가 놓치는 의미 오류의 규모를 *정량 기술*한다. 단독 탐지율은 새 표준 지표를 제안하는 것이 아니라 *NLI 검증 축의 진단 기여를 가시화하는 보조 도구*이며, 분모는 BIRD gold 실행 결과(외부 정답 기준)에 의존한다.

3. **[방법론] 오류 유형 기반 분기 교정기(Type-Routed Corrector)** — 오류를 8개 유형(스키마·구문·조인·집계·필터·프로젝션·빈 결과·의도 불일치)으로 분류하고, 각 유형에 대응하는 전용 교정 프롬프트를 라우팅한다. 단일 공용 교정기 대비 특히 의미·구조적 오류 유형(E3 조인, E4 집계, E_intent)에서 교정 정확도를 향상시킨다는 가설을 검증한다.

4. **[방법론] Self-Consistency 결합 — 응답 다양성을 의미 검증과 결합** — 동일 프롬프트에 대해 temperature=0(결정론적) 1회와 temperature=0.7(다양화) k-1회로 총 k=5개의 SQL 후보를 생성하고, 각 후보의 *실행 결과 지문(fingerprint)* 다수결로 단일 SQL을 선택한다. 이 결과 선택기를 NLI 의미 검증과 결합하면 (i) 실행으로 살아남은 후보 중 결과 동치 군집을 선호하면서 (ii) 실행 통과 + 결과 동률인 실행 통과 오답 영역에서는 의도 정합성 점수(Intent Consistency Score, ICS)로 추가 변별이 가능해진다. Self-Consistency(k=5)는 상위 시스템(CHASE-SQL, Agentar-Scale-SQL)에서도 핵심 구성 요소로 채택되어 있어, 본 연구의 다른 기여와 별도 축으로 결합 가능한 *차용 기법*에 해당한다.

5. **[평가 인프라] 한국형 기업 도메인 평가 표준** — 세 가지를 표준화한다. 첫째, 기업 인사 DB의 DDL과 외래키만 이식하고 행은 합성으로 채우는 **스키마-온리 평가 프로토콜**로, 개인정보 제약 환경에서도 Text-to-SQL의 사전 검증을 가능하게 한다. 둘째, **공정 비교 재실행 인프라**로 DAIL-SQL과 MAC-SQL 공식 구현을 동일한 gpt-4o-2024-11-20 백본으로 래핑하고 BIRD 공식 평가 스크립트(`evaluation.py`)로 일괄 측정해, 인용 수치 혼용으로 인한 비교 편향과 자체 평가 로직 차이로 인한 측정 편향을 동시에 제거한다(DIN-SQL 경량 래퍼는 본 연구 범위에서 측정 미완료 상태이며 향후 측정 항목으로 분류한다). 셋째, HRDB 합성 평가셋을 수동 시드 30개에서 **5 페르소나(인사 운영, 급여, 인사 기획, 근태, 휴가) × 3 난이도 × 자동 검증 통과**로 257개까지 확장해 페르소나 간 비교가 가능한 통계 검정력을 확보한다.

6. **[운영 가이드라인] 강한 LLM 환경의 검증 축 운영 패턴** — 위 정량 결과로부터 GPT-4o급 백본을 사용하는 실무 환경에서 **NLI 검증 결과별 권장 액션**(자동 교정, 사용자 경고, 휴먼-인-더-루프(HITL) 트리거, 무시)을 결정하는 운영 표(§6.2 표 10)를 도출한다. 이는 "NLI는 EX를 올리지 않으니 무용하다" 또는 "NLI는 항상 교정 트리거이다" 같은 단순 결론을 회피하고, *SQL 신뢰도, 실행 결과 상태, NLI 점수, 결과 다수결 일치도*의 결합 조건에 따른 단계별 운영 가이드를 제시한다. 운영 가이드라인은 본 연구의 단독 탐지율 68.1% 관측을 HITL 분류(triage) 임계값 설계의 정량 근거로 환원한다.

본 기여들은 "비전공 실무자가 자연어로 즉시·안전하게 기업 데이터에 접근한다"는 상위 목표(기여 1)와, 이를 정확·재현 가능한 형태로 달성하기 위한 방법론적 결정(기여 2~4), 평가 표준(기여 5), 그리고 *결과 해석을 운영 의사결정으로 환원*하는 가이드라인(기여 6)을 일관된 흐름으로 연결한다.

본 논문에서 사용하는 모든 베이스라인 수치는 저자가 동일 백본으로 *재실행한 결과*이며, 원 논문의 인용 수치(GPT-4 + Self-Consistency 기반)와 다를 수 있다. 이 차이는 §5.3과 §5.4에서 명시한다. 본 연구의 비교 주장은 "원 논문 수치의 복제"가 아니라 **"동일 백본·동일 평가 프로토콜 조건에서의 상대 성능"**으로 한정한다.

## 제2장 관련 연구

본 장은 Text-to-SQL 및 자기교정 계열 선행 연구를 네 축으로 정리한다: (2.1) 기술 발전 궤적, (2.2) 자기교정·오류 인식, (2.3) NLI 기반 의미 검증, (2.4) 에이전트 기반 LLM 시스템. 각 축 말미에서 본 연구와의 차별점을 명시한다.

### 2.1 Text-to-SQL 기술의 발전

초기 Text-to-SQL은 시퀀스-투-시퀀스 신경망 기반의 구문 유도(grammar-guided) 디코딩이 주류였다. 이후 Spider 벤치마크의 도입으로 cross-domain 일반화가 요구되기 시작했고, PICARD·RAT-SQL 등 스키마 링킹과 제약 기반 디코딩을 결합한 기법들이 제안되었다. 그러나 이러한 신경망 특화 구조는 고비용 학습과 도메인 이전의 어려움이라는 한계를 가졌다.

LLM의 등장 이후 **in-context learning** 패러다임이 지배적 접근이 되었다. DAIL-SQL[^2]은 질의의 *구조 유사도*와 *의미 유사도*를 결합해 few-shot 예시를 선택하는 전략으로 BIRD·Spider 양쪽에서 당시 SoTA를 달성했다. DIN-SQL[^4]은 난이도를 단순·비집계·집계·복합으로 분해하고, 각 난이도에 맞춘 프롬프트를 차례로 적용하는 분해형 접근을 제시했다. CHESS[^8]는 스키마 선택-SQL 생성-검증 세 단계를 명시적으로 구조화해, 스키마 링킹 품질 개선이 전체 EX에 미치는 영향을 체계적으로 실증했다.

최근에는 대규모 벤치마크인 **BIRD**[^1]의 등장이 주요한 전환점이다. BIRD는 (a) 외부 지식(evidence)을 질의와 함께 제공하며 (b) 실행 효율성을 함께 측정하는 VES(Valid Efficiency Score)를 도입해, Spider 대비 훨씬 실무에 가까운 난이도와 평가 축을 제공한다.

**본 연구와의 차별점.** 상기 연구들은 **생성 품질**을 개선하는 데 초점이 있으며, 일단 생성된 쿼리가 *의도와 일치하는가*는 명시적 검증 대상이 아니다. 본 연구는 생성 품질을 별도로 개선하지 않고, **생성 이후의 검증-교정 축**에서 의도 정합성 차원을 도입함으로써 별도 차원의 개선을 목표로 한다.

### 2.2 SQL 자기교정 및 오류 인식

자기교정 계열은 크게 **(A) 실행 기반 재시도**, **(B) 오류 분석 기반 재작성**, **(C) 다중 에이전트 정제**로 분류된다.

- **(A) 실행 기반 재시도.** 가장 단순한 접근은 생성 쿼리를 실행하고 오류가 발생하면 오류 메시지를 프롬프트에 추가해 재시도하는 방식이다. 이는 구현이 간단하나 *실행 성공 ≠ 의도 일치*인 경우에 대해 무력하다.
- **(B) 오류 분석 기반 재작성.** SQLens[^9]는 SQL 실행 계획·결과 통계를 분석해 의심되는 절(clause)을 식별하고, 절 단위로 LLM이 재작성하도록 유도한다. "A Study of In-Context-Learning-Based Text-to-SQL Errors"[^10]는 GPT-계열 모델이 범하는 오류를 8개 유형으로 분류하고, 각 유형의 빈도·교정 난이도를 실증적으로 보고했다. SQL-of-Thought[^11]은 SQL 생성 과정을 CoT 형태로 풀어 중간 추론 단계에서 스스로 오류를 감지하게 한다. SQLDriller[^12]는 실행 결과의 row 개수·분포 이상을 감지해 재작성 트리거로 사용한다.
- **(C) 다중 에이전트 정제.** MAC-SQL[^5]은 Selector(스키마 선택)·Decomposer(질의 분해)·Refiner(정제) 세 역할을 분리해 협업한다. SQLFixAgent[^6]·MAGIC[^7]은 *교정 전용 에이전트*를 두어 오류 패턴을 수집·학습하고, 이를 다음 생성에 피드백한다.

이들 접근 모두 검증 축에서 **실행 가능성·결과 동치성·SQL 절 구조** 중 하나를 기반으로 삼는다. 즉 검증의 관점이 *SQL 코드 또는 그 실행 결과*에 갇혀 있어, 쿼리가 성공적으로 실행되고도 의도와 다른 결과를 내는 경우(예: 조건 누락, 집계 범위 오해)를 구조적으로 놓친다.

**본 연구와의 차별점.** 본 연구는 검증 축에 **자연어 수준의 의미 일치**라는 새로운 차원을 추가한다(§2.3). 또한 교정 측면에서도, 선행 연구가 오류 유형을 *진단*까지는 수행하면서도 실제 교정에는 동일한 프롬프트를 사용하는 경향이 있다는 점을 지적하고, **유형별 전용 교정 지시문**으로 한 단계 더 나아간다.

### 2.3 자연어 추론(NLI) 기반 의미 검증

자연어 추론(NLI)은 전제(premise)와 가설(hypothesis) 사이의 함의(entailment)·중립(neutral)·모순(contradiction) 관계를 판정하는 과업으로, SNLI·MultiNLI·ANLI 등의 대규모 데이터셋과 RoBERTa·DeBERTa 계열 cross-encoder 모델이 표준적으로 사용된다. Text-to-SQL 외부 맥락에서 NLI는 *요약 사실성 검증*, *RAG 답변 검증* 등 생성 결과의 의미 일관성을 확인하는 데 광범위하게 응용되어 왔다.

Text-to-SQL 영역에서도 제한적이지만 **SQL→NL 역번역**을 활용한 검증 시도가 있다. 대표적으로, 생성된 SQL을 다시 자연어로 풀어 쓰고 원 질의와 의미를 비교함으로써 *의도 보존 여부*를 확인하는 접근이다. 그러나 기존 시도들은 (i) 역번역과 원 질의를 단순히 LLM에 동시에 제시해 "같은가"를 물어보는 *LLM-as-judge* 방식을 사용하거나, (ii) 역번역을 생성해 두더라도 그 결과를 *검증* 단계에 공식적으로 편입하지 않고 *설명* 용도로만 사용하는 데 그쳤다.

**본 연구와의 차별점.** 본 연구는 (a) 역번역 결과를 **별도의 NLI 모델**로 판정해 LLM-as-judge의 비결정성·비용 문제를 회피하고, (b) NLI 결과를 **의도 정합성 점수(ICS)** 라는 정량 지표로 정의해 임계값 기반 *교정 트리거*로 사용하며, (c) 이 축을 실행 검증과 **병렬로** 배치해 두 축이 독립적으로 기여하는지를 어블레이션으로 분리·측정 가능하게 설계했다는 점에서 차별화된다.

### 2.4 에이전트 기반 LLM 시스템

단일 프롬프트를 넘어 여러 전문 에이전트를 조합하는 접근은 Text-to-SQL을 포함해 여러 생성 과업에서 성능 향상을 보여 왔다. MAC-SQL[^5], CHESS[^8], MAGIC[^7]은 선택·분해·검증·교정을 별도의 프롬프트 페르소나로 나눈다. 최근 PV-SQL[^20]은 데이터베이스 직접 probing과 규칙 기반 검증을 결합한 에이전트 시스템을 제안해, *검증 단계의 외부 신호 다양화*가 자기교정 계열의 한 발전 방향임을 보였다. LangGraph·AutoGen 등의 에이전트 오케스트레이션 프레임워크는 조건부 분기와 상태 전이를 명시적으로 관리하게 해, 기존의 연쇄 프롬프트(chain)보다 제어 가능한 파이프라인을 구성하게 한다.

에이전트 구성에서 중요한 설계 쟁점은 **(i) 에이전트 간 인터페이스의 명확성**, **(ii) 반복 루프의 종료 조건**, **(iii) 실패 경로의 복구**이다. 본 연구의 SC-TSQL은 LangGraph 기반 상태 머신으로 구현되어 있으며(§4.1), 각 에이전트는 TypedDict로 명세된 상태 필드만 읽고 쓴다. 종료 조건은 "실행 성공 AND ICS ≥ θ"의 합집합이며, 최대 반복 K=3으로 비용 상한을 강제한다.

**본 연구와의 차별점.** 선행 에이전트 시스템 대부분이 "생성→검증→정제"의 일관된 단일 경로를 사용하는 반면, 본 연구는 검증 축 자체를 *이중화*(실행 축 + 의미 축)하고, 정제 경로를 *오류 유형별로 분기*함으로써 상태 공간을 명시적으로 확장한다.

## 제3장 오류 유형 분석

### 3.1 오류 분류 체계

자기교정이 효과를 내려면 오류의 원인을 정확히 진단하는 단계가 선행되어야 한다. 본 연구는 선행 연구[^10]가 제안한 Text-to-SQL 오류 유형 체계를 기반으로, 실행 축에서만 포착되는 7개 유형(E1–E7)과 본 연구가 추가한 **의미 축 전용 유형** E_intent를 결합해 총 8개 유형으로 정의한다(표 1).

**표 1. 오류 유형 분류 체계 및 감지 근거**

| 코드 | 유형 | 감지 근거 | 검증 축 |
|---|---|---|---|
| E1 | Schema Mismatch | 존재하지 않는 테이블/컬럼 참조 | 실행 |
| E2 | Syntax Error | 파서 에러 | 실행 |
| E3 | Join Error | 잘못된 JOIN 키 / 누락된 JOIN | 실행 |
| E4 | Aggregation Error | GROUP BY / 집계함수 오류 | 실행 |
| E5 | Filter Error | WHERE 조건 불일치 | 실행 |
| E6 | Projection Error | SELECT 컬럼 불일치 | 실행 |
| E7 | Empty/Timeout | 결과 0행 또는 타임아웃 | 실행 |
| **E_intent** | **Intent Mismatch** | **NLI entailment < θ** | **의미(본 연구 신규)** |

복수 유형이 동시에 감지될 경우 우선순위는 **E2 > E1 > E3 > E4 > E5 > E6 > E7 > E_intent**이다. 이는 *저수준 오류(구문·스키마)가 상위 수준 의미 판단보다 먼저 해결되어야* 한다는 원칙을 반영한다. 즉 E_intent는 실행 축이 모두 통과한 뒤에만 발동하는 **최종 의미 안전망**으로 위치시켰다.

각 유형에 대응되는 교정 지시문(§4.4.4)은 다음과 같은 원칙으로 설계되었다.
- **E1**: 스키마 재링킹 결과를 프롬프트 상단에 강조하고, 잘못 사용된 식별자를 명시적으로 지적.
- **E2**: 파서 오류 메시지와 최소 구문 수정 예시를 포함.
- **E3**: 외래키 관계 그래프와 올바른 JOIN 경로를 시각화해 주입.
- **E4**: 집계 대상·GROUP BY 키를 명시적으로 재확인하도록 요구.
- **E5**: 조건 값의 범위·단위·날짜 포맷을 재해석하도록 지시.
- **E6**: 사용자가 요구한 출력 컬럼 집합을 다시 정리해 주입.
- **E7**: 필터 완화 및 인덱스 힌트.
- **E_intent**: 역번역 문장과 원 질의의 차이를 자연어로 대조시켜, 의미 차이를 *무엇을 반영하지 않았는지* 관점에서 지적.

### 3.2 오류 분포 실증 분석

본 연구는 SC-TSQL의 최종 결과 단계 쿼리에 대해 **두 검증 축의 집합 차(set difference)**를 정량화한다. 본 실험(BIRD n=300, GPT-4o, 2026-05-01)에서 관측된 4-cell 분포는 다음과 같다.

**표 2. 검증 축의 4-cell 분포 — Full SC-TSQL (BIRD n=300)**

| | NLI 일치 (ICS ≥ 0.75) | NLI 불일치 (ICS < 0.75) | 행 합계 |
|---|---:|---:|---:|
| **실행 통과 + 정답 (EX=1)** | 56 | 95 | 151 |
| **실행 통과 + 오답 (EX=0, 실행 통과 오답 영역)** | 46 (잔여) | **98** (NLI 단독 탐지) | 144 |
| **실행 실패** | 0 | 5 | 5 |
| **열 합계** | 102 | 198 | 300 |

이 분포에서 본 연구의 핵심 신지표가 직접 산출된다.

- **단독 탐지율** (실행 검증을 통과했지만 외부 정답과 다른 *실행 통과 오답 영역* 144건 중 NLI가 단독으로 의심 신호를 출력한 비율) = 98건 / 144건 = **68.1%**.
- 즉 **실행 검증이 통과시켰음에도 실제로는 오답인 실행 통과 오답 쿼리의 약 2/3을, NLI가 단독으로 의심 신호로 표시**한다.
- 이는 실행 축과 NLI 축이 *서로 다른 오류 집합*을 포착함을 의미하며, NLI를 EX 보조 지표가 아닌 **독립 진단 축**으로 배치할 정량적 근거가 된다.
- **잔여 오답 영역(46건, 양 축 모두 통과한 오답)** 은 본 시스템도 포착하지 못한 영역으로, 한국어 NLI 모델 도입·HITL(Human-in-the-Loop) 등의 향후 과제로 연결된다(§6.4).

**Consistency@0.75 = 34.0%, ICS mean = 0.540** (n=300). NLI는 전체 질의의 66%에서 *불일치* 신호를 발하는데, 이 중 실제로 오답인 비율이 위 표의 두 번째 행 우측 열(98/198 = 49.5%)이다. 즉 *NLI 불일치 신호의 약 절반이 실제 오답 탐지로 이어진다*.

본 실험 CSR(Correction Success Rate) = 20.0%로, 자기교정 루프가 발동한 쿼리 중 1/5에서 실제로 EX가 회복되었다. 이는 교정 빈도와 교정 성공률이 모두 비제로(non-zero)임을 의미하며, *역번역-NLI가 불일치를 탐지하는 능력*과 *교정기가 그 불일치를 해소하는 능력*이 별개의 과제이지만 본 시스템에서 양쪽 모두 부분적으로 성립함을 시사한다.

HRDB 환경(30개 질의, 577개 테이블 중 주요 7 테이블 사용, Oracle-style 영문 컬럼명)에서는 한글 도메인 용어(예: "재직자", "부장 이상", "개발본부")와 영문 컬럼명과 의미 명칭의 불일치(예: `SABUN`=사원번호, `JIKGUB_NM`=직급명 vs `JIKCHAK_NM`=직책명)의 존재로 **E1(Schema Mismatch)** 의 비중이 크게 증가한다. 파일럿(n=10, GPT-4o-mini)에서 한글 컬럼 설명 메타데이터를 FAISS 인덱스와 LLM 후보 제시 단계에 주입했을 때 SC-TSQL의 EX가 **20% → 40%**(+20pp)로 상승했다.

RQ1 진단 가설의 정성 임계값 단독 탐지율 ≥ 30%는 분석 보고 시점에 *진단 가설 지지의 보조 판단 기준*으로 도출된 값이며, **사전 등록 임계값이 아니다**. RQ1의 결정 자체는 표 2의 4-cell 분포에서 *실행 통과 + 오답 영역 144건 중 NLI 단독 탐지 98건*이라는 *단독 탐지 패턴* 으로부터 도출되며, 30% 임계값은 본 패턴을 *가시화하는 보조 기준* 에 한정해 사용한다. 본 임계값 선택의 결과 친화성 차단을 위해, 단독 탐지율은 §6.4 한계 12의 임계값 sensitivity 측정 범위(표 7 (a)·표 7 (b), §5.5)와 함께 인용함이 옳다. 이는 실무 DB의 명명 규약이 스키마 링킹 품질에 결정적 영향을 줌을 실증한다(§6.4 상술).[^16]

[^16]: 본 임계값(단독 탐지율 ≥ 30%)은 분석 보고 시점에 *진단 가설 지지의 보조 판단 기준* 으로 도출되었으며, **사전 등록 임계값이 아니다**. RQ1 결정 자체는 표 2의 4-cell 분포에서 관측된 *단독 탐지 패턴*(실행 통과 + 오답 144건 중 NLI 단독 탐지 98건)으로부터 도출되며, 30% 임계값은 가시화 보조에 한한다. *사전 등록 임계값 부재* 는 본 연구의 한계이며, 향후 OSF 등 외부 사전 등록 절차를 동반한 후속 검증이 필요하다(§6.4 한계 7).

## 제4장 제안 프레임워크 (SC-TSQL)

### 4.1 시스템 아키텍처 개요

SC-TSQL은 자연어 질의 `q`와 데이터베이스 식별자 `db_id`, 선택적 외부 증거 `evidence`를 입력으로 받아 정답 SQL `s*`와 실행 결과를 출력하는 파이프라인이다. 시스템은 5개 주요 모듈로 구성된다(그림 1).

```
                 ┌──────────────────────────────────────────────┐
                 │  q, db_id, evidence                          │
                 └─────────────────┬────────────────────────────┘
                                   ▼
                      [1] Schema Linker
                                   ▼
                      [2] SQL Generator (GPT-4o few-shot)
                                   ▼
         ┌─────────────────────────┴──────────────────────────┐
         │              [3] Self-Correction Loop              │
         │                                                    │
         │    ┌── Execution Validator  (E1~E7) ───┐           │
         │    │                                    │           │
         │    └── Intent Consistency Checker ──────┤ OR  fail? │
         │        (SQL→NL 역번역 + NLI, E_intent)   │           │
         │                                   ▼  ▼             │
         │                        [Error Classifier]          │
         │                                   ▼                │
         │                   [Type-Routed Corrector]          │
         │                                   ▼                │
         │              (재검증 ↑ loop, max K=3)              │
         └─────────────────────────┬──────────────────────────┘
                                   ▼
                   [4] Result Explainer → s*, 결과
```

**그림 1. SC-TSQL 전체 아키텍처.** 실행 검증과 의도 정합성 검증이 병렬 배치되어 *OR*로 통합되며, 교정기는 진단된 오류 유형에 따라 분기된다.

구현은 LangGraph 상태 머신으로 이루어져 있으며, 상태는 TypedDict로 명세되어 모듈 간 인터페이스가 정적으로 고정된다. 각 모듈은 상태 필드를 읽고 쓸 뿐 다른 모듈을 직접 호출하지 않는다.

### 4.2 스키마 링커

스키마 링커는 `q`와 `db_id`를 입력으로, 후속 단계가 참고할 관련 테이블·컬럼 스니펫 `schema_context`를 반환한다. 두 단계로 동작한다.

1. **벡터 검색.** 각 테이블·컬럼의 명세(이름·타입·코멘트)를 `text-embedding-3-large`로 임베딩한 뒤, `q`와의 코사인 유사도로 top-K 후보를 선별한다(표 K=10, 컬럼 K=30).
2. **LLM 재선택.** top-K 후보와 외래키 관계 그래프를 LLM에 제시해, 최종적으로 사용할 테이블·컬럼 집합을 JSON으로 선별·정리한다.

이 두 단계 구성은 CHESS[^8]와 유사하나, 본 연구는 LLM 재선택 시 *사용자 질의에 없더라도 JOIN 경로상 필수인 브리지 테이블*을 명시적으로 포함하도록 지시해, 후속 E3(Join Error) 발생을 선제적으로 억제한다.

### 4.3 SQL 생성기

SQL 생성기는 `q`, `schema_context`, `evidence`, few-shot 예시를 조합해 SQL 초안 `s_0`을 생성한다. 백본은 **gpt-4o-2024-11-20**(temperature=0, seed=42)로 고정한다.

**Few-shot 선택**은 DAIL-SQL[^2]의 *구조·의미 유사도 가중합* 방식을 차용해, 훈련 풀(BIRD train)에서 구조 유사도(스키마 중첩도·절 패턴)와 의미 유사도(문장 임베딩)를 각 0.5 가중으로 합산해 상위 3개 예시를 선택한다.

**Pre-finalization 체크리스트 기반 CoT.** 생성 프롬프트 말미에 *Intent → Tables/joins → Filters → Aggregation → Output columns* 5단계 체크리스트를 두어, LLM이 SQL을 작성하기 *전* 에 의도와 스키마 정합성을 자가 점검하도록 강제한다. 이 체크리스트는 한국형 인사 도메인(§4.5)에서 (a) JOIN 값 도메인 안전성, (b) `_CD`/`_NM` 페어 동시 SELECT, (c) 시간 표현 cut-off (CURRENT_DATE 주입) 같은 흔한 결함을 사전 차단하는 데 효과적이다.

#### 4.3.1 Self-Consistency (k=5) 결합

본 연구는 BIRD 리더보드 상위 시스템(CHASE-SQL[^13] · Agentar-Scale-SQL[^15])에서 검증된 **Self-Consistency(SC)**[^22] 를 SQL 생성기에 결합한다. 단일 결정론 호출 1회와 temperature=0.7 다양화 호출 (k−1)회로 총 k=5개 후보를 *병렬* 생성하고, 각 후보를 실행 검증기에 통과시킨 뒤 살아남은 후보들의 **결과 핑거프린트(SHA-256)** 다수결로 단일 SQL을 선택한다. 결과 핑거프린트는 행 집합을 정렬해 직렬화 한 후 해시하므로, 텍스트가 다르더라도 같은 결과를 반환하는 SQL은 같은 그룹으로 묶인다.

이 결합은 두 가지 효과를 제공한다.

1. **다양성 → 단일 잘못된 시도 회피.** k=1에서는 첫 시도가 잘못된 방향이면 자기교정 루프 안에서도 그 방향에 갇힐 수 있지만, k=5에서는 다양화된 후보 중 적어도 하나가 정답에 가까울 확률이 높다.
2. **NLI selector와의 독립 결합.** 결과 동률 그룹이 여러 개일 때(예: 두 후보가 서로 다른 결과를 동수 표결), NLI ICS 점수로 *의미 일치도가 높은* 그룹을 선호하도록 추가 변별이 가능하다. 본 구현에서는 다수결 그룹 내에서 평균 confidence가 높은 후보를 선택하며, 의미 변별은 후속 단계(§4.4.2 ICC)에 위임한다.

SC를 추가함에 따라 응답 시간은 단일 호출 대비 약 3~4배(병렬화로 5배가 아닌 3.5배 수준)이고 LLM 토큰 비용은 약 5배가 된다. 본 연구는 이 비용 증가를 수용하는 대가로 EX 향상을 시도하며, **SC의 단독 기여는 어블레이션 변형 `no_sc`(k=1로 강제) 와의 비교**로 분리 측정한다.

생성기는 SQL 한 줄만 반환하며, 후속 단계가 구문 파싱을 수행한다.

### 4.4 자기교정 루프

자기교정 루프는 `s_0`을 입력으로 받아, 최대 K=3 라운드 동안 검증-교정을 반복한다. 각 라운드는 (i) 실행 기반 검증기, (ii) 의도 정합성 검증기, (iii) 오류 분류기, (iv) 유형별 교정기를 차례로 수행한다. 종료 조건은 "실행 성공 AND ICS ≥ θ" 또는 "라운드 수 = K"이다.

#### 4.4.1 실행 기반 검증기

읽기 전용 SQLite 연결로 `s_t`를 실행하며, 5초 타임아웃과 row 개수 상한을 적용한다. 출력은 (a) 실행 성공 여부, (b) 오류 유형 코드(E1–E7 중 하나 또는 success), (c) 반환 row 수, (d) 실행 시간이다. 오류 메시지 파싱은 SQLite가 반환하는 원문 문자열에 대한 정규식 매칭(`no such table`, `no such column`, `syntax error`, `datatype mismatch` 등)과 AST 분석을 결합한다.

#### 4.4.2 의도 정합성 검증기 (NLI 기반)

**의도 정합성 검증기(Intent Consistency Checker, ICC)** 는 본 연구의 핵심 모듈로, 다음 세 단계로 구성된다.

1. **역번역.** 현재 SQL `s_t`와 `schema_context`를 LLM에 제시해, "이 SQL이 무엇을 묻는 쿼리인지 자연어 한 문장으로 풀어 쓰시오"라는 프롬프트로 역번역 문장 `q'`를 얻는다. 이때 LLM은 *SQL→NL* 방향에만 특화된 시스템 프롬프트를 사용하며, *SQL의 의미를 풀어쓰는 의무는 유지* 하되 **사용자 영문 질의 `q_en` 의 어휘 풀(noun/verb)을 어휘 정렬 힌트로 함께 제시** 한다. 이는 SQL→NL 변환 LLM과 한국어→영어 변환 LLM이 서로 다른 영어 어휘를 선택해 NLI가 *의미는 같지만 어휘 다른* 입력을 받게 되는 *어휘 갈라짐* 문제(시연 진단에서 ICS 0.4 미만 사례 다수 관측)를 완화한다. 단, 원 질의 문장의 *그대로 복제* 는 금지하여 §6.4 한계 #4(역번역의 모사 위험)와 균형을 맞춘다.
2. **NLI 판정.** 원 질의 `q`를 전제, 역번역 `q'`를 가설로 삼아 `cross-encoder/nli-deberta-v3-base`[^21] 모델로 `P(entailment), P(neutral), P(contradiction)` 세 확률을 얻는다. 반대 방향(전제·가설 교환)도 동일하게 수행해 가중평균(`0.6·forward + 0.4·backward`)을 취함으로써 비대칭성을 보정한다.
3. **ICS 산출 및 트리거.** 의도 정합성 점수를 `ICS = 0.6·P_fwd(entailment) + 0.4·P_bwd(entailment)` 로 정의하고, NLI 불일치(SQL→NL → user_NL contradiction) 임계값 **θ_trig = 0.6** 미만이면 E_intent를 발생시켜 교정 루프를 트리거한다. 본 임계값은 §5.1.1의 `semantic_threshold = 0.75`(보고 지표 임계값 θ_rep)와는 **개념·용도가 분리된** 별개의 trigger 임계값이다.

**이중 임계값의 정의 (시연 진단 후 갱신).** 본 연구는 두 가지 임계값을 *분리하여 정의·운영*한다.

- **(a) 교정 트리거 임계값 θ_trig = 0.6** — ICC가 자기교정 루프를 발동시키는 결정 기준이며, NLI 불일치(SQL→NL → user_NL contradiction) trigger 비율 sweep(표 7 (a))에서 채택한 운영값. DeBERTa-NLI v3가 *의미 일치하더라도 어휘가 다른* paraphrase에 대해 entailment 확률 0.4~0.7대를 출력해 사용자 인식상 거짓 경고가 다수 발생하는 문제가 시연 진단(2026-04)에서 관측되어, 0.75 → 0.6으로 완화하였다.
- **(b) 보고 지표 임계값 θ_rep = 0.75** — `Consistency@θ_rep`(§5.2.2)와 표 2의 4-cell 분포 라벨링에 사용되는 *외부 보고용* 기준. 0.75는 selfcheck-sql 등 선행 연구의 entailment 절대 우위 관행에 정렬한 값이다.

**θ_trig 와 θ_rep 의 분리.** θ_trig 는 NLI 불일치 *trigger 발동* 결정에 사용되며 본 연구의 운영값은 0.6이다. θ_rep 는 4-cell 분포 라벨링과 단독 탐지 분자 정의에서 사용되며 0.75이다. 두 임계값에 대한 sensitivity sweep은 §5.5 표 7 (a)(trigger 비율 by τ)와 표 7 (b)(단독 탐지율 by τ)에서 분리 보고한다.

두 임계값을 분리한 이유는 *교정 결정에 보수적인(entailment 우위만 정상 처리) 운영 정책*과 *보고 지표의 외부 비교 가능성*이 서로 다른 목적을 가지기 때문이며, 단독 탐지율 산출 시에는 *분자 정의에서 θ_rep를 사용*하여 외부 비교 가능성을 확보한다. 두 임계값에 대한 단독 탐지율·Consistency 민감도는 BIRD dev_300의 NLI raw 점수 로그 보존 여부에 따라 부록 C에 sweep 형태로 보고할 계획이며, 본 연구의 측정 범위는 §6.4 한계 12에 명시한다.

#### 4.4.3 오류 분류기

실행 검증과 의도 정합성 검증 결과를 통합해 오류 유형 코드를 결정한다. 알고리즘은 다음과 같다.

```
if exec_result.status == "success":
    if ICS >= θ:
        return SUCCESS     # 교정 불필요
    else:
        return E_intent
else:
    return exec_result.error_code  # E1~E7
```

즉 E_intent는 실행 축이 **모두 통과**했을 때만 발동한다. 이는 저수준 오류가 남아 있는 상태에서 NLI를 수행하는 것이 비효율적이며 잡음이 크기 때문이다.

#### 4.4.4 유형별 교정기

교정기는 오류 유형 코드를 키로 삼아 유형별 전용 프롬프트를 선택한다(§3.1 표 1). 각 프롬프트는 공통 스켈레톤과 유형별 차이 섹션으로 구성된다:

- **공통 섹션**: 원 질의, 스키마 스니펫, 현재 SQL, 외부 증거.
- **유형별 섹션**: 해당 유형에 특화된 힌트·예시·금지 사항.

예를 들어 **E_intent 교정 프롬프트**의 유형별 섹션은 다음 구조를 갖는다:

```
[Intent Mismatch Correction]
- 사용자의 원 질의는 다음과 같다: {q}
- 현재 SQL의 역번역은 다음과 같다: {q'}
- 두 문장의 차이는 주로 {NLI 모델이 판단한 불일치 단서}에 있다.
- 위 차이를 SQL에 반영해, 사용자의 의도를 더 정확히 표현하도록 수정하시오.
- 단, 스키마에 존재하는 컬럼만 사용해야 한다.
```

이에 비해 **E3 Join Error 교정 프롬프트**의 유형별 섹션은 외래키 경로 그래프를 제시하고, "가능한 JOIN 경로는 다음 중 하나이다"라고 열거하는 방식으로 매우 다르다. 이처럼 *무엇이 틀렸는지*에 따라 LLM에 서로 다른 편향을 주입하는 것이 본 연구의 RQ2 핵심 주장이다.

단일 공용 교정기와의 비교는 §5.5(A3 어블레이션)에서 보고한다.

### 4.5 한국형 기업 도메인 적응 설계

기존 Text-to-SQL 연구의 대부분은 영어 자연어와 영어 컬럼명(`employees.salary`, `departments.name` 등 *의미가 자연어로 직접 노출*되는 명명)을 전제로 한다. 그러나 한국 기업 환경에서 사내 관계형 DB는 통상 다음 세 가지 *구조적 특수성(asymmetry)*을 동시에 가진다.

**(가) 자연어와 영문 컬럼명의 의미 비대칭.** 사용자는 한국어로 "직급별 평균 급여"를 묻지만, 본 연구의 HRDB는 `THRM151.JIKGUB_NM`·`TCPN303.TOT_EARNING_MON`처럼 8자 영문 약어로 컬럼을 정의한다(이러한 명명 관습은 본 연구의 HRDB 환경 — Oracle 기반 인사 시스템 — 의 특성이며, 한국 기업의 모든 사내 시스템이 동일한 패턴을 가지는 것은 아니다). LLM이 영어 사전적 의미만으로 이 매핑을 해결하는 것은 어렵다. 본 연구는 [데이터 사전](data/raw/hrdb/column_descriptions.json) 형태의 *영문 컬럼명 → 한글 의미* 매핑을 [SchemaLinker](src/schema_linker.py)가 자동으로 로드해 (i) FAISS 임베딩 인덱스 구성 시 한글 의미를 텍스트에 포함하고, (ii) LLM 프롬프트의 `CREATE TABLE` 주석으로 주입한다. 이로써 LLM은 한국어 자연어에서 한글 의미를 거쳐 컬럼에 도달하는 *세 단계 매핑*을 안정적으로 수행한다.

**(나) 코드/명칭 페어의 값 도메인 비대칭.** 기업 시스템에는 동일 의미의 두 컬럼이 *서로 다른 값 도메인*으로 공존하는 패턴이 널리 사용된다. 예를 들어 `THRM151`은 직급을 `JIKGUB_CD = 'J05'` (코드)와 `JIKGUB_NM = '차장'` (명칭) 두 컬럼으로 동시에 보관한다. LLM이 자연어 "직급별"을 받았을 때 `T1.JIKGUB_CD = T2.JIKGUB_NM` 형태로 *서로 다른 도메인의 컬럼을 직접 매칭*하면 0행이 반환되는 침묵 실패가 발생한다. 본 연구는 (i) [SchemaLinker](src/schema_linker.py:_detect_code_name_pairs)가 페어 컬럼을 자동 탐지해 schema text 상단에 "JOIN safety hints" 헤더를 부착하고, (ii) [SQLGenerator](src/sql_generator.py) 가이드에 *code-to-code 또는 name-to-name으로만 JOIN하라*는 규칙을 명시함으로써 이 침묵 실패를 사전 차단한다.

**(다) 이력 테이블의 시점 비대칭.** 인사·재무 시스템은 갱신 시 새 행을 추가하고 종료일(`EDATE`)로 이력을 닫는 *append-only 이력 테이블* 패턴이 일반적이다. "재직 중"이라는 자연어는 `STATUS_CD = 'S10' AND EDATE IS NULL`이라는 *복합 조건*으로 옮겨야 하지만, LLM은 둘 중 하나만 사용하기 쉽다. 본 연구는 도메인 evidence(§4.3.1)로 이러한 *비즈니스 정의*를 LLM 프롬프트에 자동 주입한다.

**(라) 시간 표현의 학습 cutoff 비대칭.** "올해", "작년", "최근"과 같은 상대 시간 표현은 사용자에게는 *현재 시점*이지만 LLM 학습 cutoff (예: 2023년)로 매핑되어 침묵 실패한다. 본 연구는 SQLGenerator 프롬프트에 `CURRENT_DATE = YYYY-MM-DD` 힌트를 자동 주입하여 시점을 명시한다.

이 네 가지 적응 설계는 한국 기업 환경의 Text-to-SQL을 단순히 "영어 BIRD 벤치마크의 한국어 변형"으로 보지 않고, **한국 IT 서비스 산업 특유의 시스템 명명 관습·이력 패턴·시점 의존성**을 직접 다루는 본 연구의 차별점이다.

**표 13. 한국형 도메인 적응 설계 — 네 가지 특수성과 본 연구의 처리**

| 축 | 한국 기업 시스템 패턴 | 단순 LLM의 실패 모드 | 본 연구의 적응 설계 | 적용 모듈 |
|---|---|---|---|---|
| (가) 영문 컬럼명 ↔ 한글 의미 | `THRM151` (8자 영문 약어) | 영문 의미 사전 매핑 실패 | column_descriptions.json 자동 주입 | SchemaLinker |
| (나) 코드 ↔ 명칭 페어 | `JIKGUB_CD = 'J05'` / `JIKGUB_NM = '차장'` | `T1.X_CD = T2.Y_NM` 침묵 실패 | _CD/_NM 자동 탐지 + JOIN safety hints | SchemaLinker + SQLGenerator |
| (다) 이력 테이블 시점 | `EDATE IS NULL` = 현재 발령 | 단일 조건 누락 시 모든 이력 반환 | 도메인 evidence 자동 주입 | SQLGenerator |
| (라) 시간 표현 cut-off | "올해" → 2023 (학습 cutoff) | 사용자 의도와 어긋난 연도 | CURRENT_DATE 명시 주입 | SQLGenerator |

본 연구의 적응 설계는 한국형 인사 도메인의 합성 평가셋(HRDB n=257)에서 검증되며, *공개 영어 벤치마크에서는 거의 발생하지 않는* 네 가지 실패 모드를 모두 사전 차단하도록 설계되었다. 이러한 설계는 다른 한국 기업 도메인(재무 회계의 `_AMT`/`_CD` 페어, 운영의 시작일/종료일 이력, 고객의 가입일/탈퇴일 등)으로 즉시 일반화 가능한 *재사용 가능한 자산* 으로 위치한다(§6.5).

### 4.6 시연 시스템 (Service-as-Implementation)

본 연구의 상위 기여(§1.3 기여 1)는 비전공 실무자가 *서비스 형태*로 직접 사용 가능한 시스템이다. 본 절은 이 시스템의 구성과 비전공 사용성을 위한 네 가지 설계 결정을 기술한다.

#### 4.6.1 시스템 아키텍처

- **백엔드.** FastAPI(Python 3.11) + SQLite. 단일 [`/api/query/stream`](backend/routers/query.py) Server-Sent Events 엔드포인트가 SC-TSQL 파이프라인의 8종 이벤트(`step`, `reasoning_chunk`, `sql_generated`, `validated`, `verified`, `corrected`, `explanation`, `result`)를 실시간 발행한다.
- **프런트엔드.** React 18 + Vite + Ant Design 5([frontend/src/pages/QueryPage.tsx](frontend/src/pages/QueryPage.tsx)). 인사 시스템에 어울리는 사내 포털 톤(헤더 그라디언트, 사용자 페르소나 표시, 페르소나 카테고리 카드)으로 구현했다.

#### 4.6.2 설계 결정

**(a) 대화형 인터페이스(채팅 패턴).** SQL 입력란이나 사전 정의된 화면 없이 자연어 질의 한 줄로 시작한다. 시스템 응답은 사용자 말풍선 + 어시스턴트 말풍선의 메신저 형식이며, 멀티턴 대화를 지원한다. 이는 "별도 화면 개발 없이" 라는 §1 동기를 UI 형태로 직접 구현한 것이다.

**(b) 추론 과정의 토큰 단위 스트리밍.** SQL 생성 LLM 호출을 OpenAI Streaming API(`stream=True`)로 수행하고, Pre-finalization 체크리스트(Intent / Tables-joins / Filters / Aggregation / Output) 토큰을 SSE `reasoning_chunk` 이벤트로 실시간 전송한다. 프런트엔드는 ChatGPT 스타일의 점진적 텍스트 표시(깜빡이는 카서 포함)로 *AI가 어떻게 사고하는지*를 비전공 사용자에게 가시화한다. 이는 신뢰감 형성의 주된 결정 요소이며, "왜 이 결과가 나왔는가"라는 사용자 의문을 즉시 해소한다.

**(c) 페르소나 기반 예시 카드.** 인사 도메인의 다섯 페르소나(인력 현황·조직·급여·근태·분석) × 4개 예시 = 20개 실무형 질의를 카테고리 카드로 제공한다. 비전공 사용자가 *어떤 질의가 가능한지*를 즉시 학습할 수 있게 하며, 본 시스템이 "별도 기능 개발 없이도 다양한 실무 도메인 질의를 다룰 수 있음"을 시각적으로 입증한다.

**(d) 응답 시간 최적화.** (i) 동일 DB·모델 조합의 SC-TSQL 인스턴스를 모듈 캐시로 재사용하여 SchemaLinker의 FAISS 인덱스 빌드 비용(임베딩 호출 1–3 s)을 첫 쿼리에만 1회 발생시킨다. (ii) 실행 검증과 NLI 의미 검증을 `ThreadPoolExecutor`로 병렬 실행하여 NLI 추론 지연(0.5–2 s)을 직렬 누적에서 제거한다. (iii) NLI 검증 내부의 SQL→EN 백번역과 query→EN 번역을 병렬화하고, EN→KR 번역은 NLI 추론과 병렬화한다. 이 세 최적화는 정확도에 영향을 주지 않으면서 시연 환경에서 *체감 응답 시간 단축*이 정성적으로 관찰된다(정량 단축률은 본 연구 범위에서 36회 측정 미확보로 향후 보고; §5.6 및 §6.4 한계 13).

#### 4.6.3 시연 시스템의 학술적 위치

시연 시스템은 단순 demo가 아니라 본 연구의 *2차 평가 자산*이다. §5.6에서 12개 페르소나 시나리오 × 3회 반복 = 36회 측정으로 (i) 정확도, (ii) 응답 시간, (iii) 자기교정 발동률, (iv) 0-shot 정답률을 보고한다. 이는 BIRD 영어 학술 벤치마크(§5.3) + HRDB 한국 실무 벤치마크(§5.4) + 시연 페르소나 평가(§5.6)의 *3중 평가 구조*를 완성하며, 본 연구의 응용 가치를 정량 근거로 입증한다.

## 제5장 실험 및 결과

### 5.1 실험 환경 및 데이터셋

#### 5.1.1 BIRD 벤치마크 환경

BIRD[^1]는 95개 도메인, 12,751개 질의-SQL 쌍, 실행 효율성 평가까지 포함하는 대규모 cross-domain Text-to-SQL 벤치마크이다. 본 연구는 공개된 **dev 세트 1,534 질의**를 사용한다. BIRD의 강점은 (a) 외부 증거(evidence)를 제공해 현실적 조건을 모사하고, (b) VES(Valid Efficiency Score)로 실행 효율까지 측정한다는 점이다.

평가 환경:
- LLM: `gpt-4o-2024-11-20`[^23], temperature=0, seed=42
- 임베딩: `text-embedding-3-large`
- NLI: `cross-encoder/nli-deberta-v3-base`
- max_rounds K=3, semantic_threshold θ_trig=0.6(NLI 불일치 trigger 비율 임계값), θ_rep=0.75(보고 지표 / 4-cell 라벨링) — §4.4.2 이중 임계값 정의 참조

본 실험은 BIRD dev 1,534 질의 중 seed=42 기반 첫 300건(`outputs/logs/results_bird_*_seed42_*.json` 파일명 prefix 기준 sample_300 split)을 사용한다. 본 split 절차는 동일 seed·동일 BIRD 공식 평가 스크립트 조건에서 재현 가능하다.

#### 5.1.2 기업 HR-DB 환경 (합성 데이터)

프라이버시 제약 환경에서의 실무형 검증을 위해, 실제 기업 인사 시스템(Oracle 기반 사내 HR 시스템)의 **DDL·외래키 관계만** 이식한 HR-DB를 구축했다. 전체 스키마 규모는 **577개 테이블**로 실제 운영 DB의 복잡도를 그대로 반영하며, 본 평가 질의가 활용하는 주요 테이블은 직원 기본정보(`THRM100`), 재직 현황(`THRM151`), 조직(`TORG101`), 급여명세(`TCPN303`), 월 근태(`TTIM413`), 연차(`TTIM511`) 등 **7개**이다. 컬럼은 Oracle-style 영문 컬럼명(예: `SABUN`=사원번호, `JIKGUB_NM`=직급명)으로 한국어 도메인 용어와 1:1 매핑되지 않아, 스키마 링킹 품질이 특히 중요한 환경이다. 행 데이터는 개인식별정보를 완전히 배제한 합성 생성기로 20명분을 채웠다.

질의 세트는 총 **30개**이며, 난이도를 simple 8·medium 12·hard 10으로 설계했다. 질의는 실제 현업 분석 요청(재직자 수, 부서별 직원 수, 급여 비교, 연차 소진율 등)을 기반으로 저자가 작성·검수하고, SQLite에서 전체 실행 가능성을 사전 검증했다. 주의해야 할 점은, HRDB는 "실무 DB의 명명 규약·스키마 복잡도가 유발하는 오류 패턴"을 검증하는 용도이며, 표본 크기 한계로 통계 검정력은 제한적이다. 실데이터 분포의 일반화는 주장 범위 밖이다(§6.3).

### 5.2 평가 지표

#### 5.2.1 실행 정확도 (EX)

`EX = | {q : exec(s_pred(q)) == exec(s_gold(q))} | / N`. 예측 SQL의 실행 결과가 gold SQL의 실행 결과와 *정확히* 일치하는 비율이다. BIRD 공식 평가 스크립트를 사용한다.

보조 지표:
- **VES (Valid Efficiency Score)**: BIRD 공식, 실행 시간 기반 효율 가중 정확도. BIRD에서만 보고.
- **EM (Exact Match)**: SQL 문자열 일치. 참고용.

#### 5.2.2 의도 정합성 점수 (Intent Consistency Score, ICS)

본 연구가 제안하는 의미 축 지표로, `ICS = mean(P(entailment(q, q')))` 로 정의한다(§4.4.2). 집계 방식은 두 가지로 보고한다.

- **ICS mean**: 전체 질의에 대한 entailment 확률 평균.
- **Consistency@θ_rep**: `ICS ≥ θ_rep=0.75` 인 질의 비율(%). 본 지표는 외부 비교 가능성을 위한 보고용이며, 교정 트리거 임계값 θ_trig=0.6과 분리된다(§4.4.2).

**중요**: ICS는 EX를 **대체하지 않으며**, 항상 EX와 병기한다. ICS 단독 향상은 의미 있지만, EX가 하락하면 trade-off를 명시적으로 논의한다.

#### 5.2.3 보조 관찰: 실행 통과 오답 영역에서의 NLI 독립 탐지 비율

본 연구는 실행 검증이 성공(no exec error)으로 판정했음에도 EX=0인 **실행 통과 오답 쿼리**에 한정해, NLI가 `ICS < θ`로 불일치를 판정한 비율을 보조 관찰로 함께 보고한다:

`(실행 통과 오답 영역 중 NLI 탐지 비율) = |{q : exec_valid(q)=True ∧ EX(q)=0 ∧ ICS(q)<θ}| / |{q : exec_valid(q)=True ∧ EX(q)=0}|`

이 비율은 새 표준 지표로 제안하는 것이 아니라, "실행 축이 통과시킨 오답 중 NLI가 얼마나 독립적으로 잡아냈는가"를 **서술적으로** 기술하기 위한 보조 관찰이다.[^17] 본 문서에서는 표·그림 라벨에서 간결성을 위해 "**NLI 독립 탐지율**"로 표기한다.

[^17]: 단독 탐지율의 분모(EX=0)는 BIRD 공식 gold execution 결과를 oracle로 사용하므로 *NLI 자기 채점*이 아닌 외부 검증된 정답 라벨에 의존한다. 그러나 분자(NLI가 ICS<θ로 단독 판정한 비율)는 NLI 모델 자체의 출력이므로, *본 비율 값이 NLI 모델 잡음을 측정한 정도*는 본 연구에서 직접 분리하지 못했다. 다른 의미 검증 도구(GPT-4o-as-judge, BLEURT 등)로 분자를 교체한 ablation은 §6.4 한계 10에 향후 과제로 명시한다.

### 5.3 비교 모델

모든 모델을 **동일 백본(gpt-4o-2024-11-20)**으로 재실행해 공정 비교 조건을 구성했다. 원 DAIL-SQL·MAC-SQL 논문이 보고한 EX는 GPT-4 세대(gpt-4-0613, gpt-4-1106-preview)와 Self-Consistency(n=5) 설정에서 측정된 것으로, 본 연구 재실행은 이 수치의 복제가 아니라 **현행 고성능 LLM(GPT-4o) 백본 및 BIRD 공식 평가 프로토콜 하에서의 상대 비교**를 목적으로 한다. 원 논문과 본 연구 재실행 간 설정 차이는 다음과 같다.

| Zero-shot GPT-4o | 스키마·질의만 제시, few-shot·교정 없음 | 기준선 |

**핵심 관측 — "고성능 LLM 환경에서 복잡 프롬프트 기법의 한계 효용":**
본 연구의 가장 두드러진 정량 발견은 **Zero-shot GPT-4o(50.7%)가 SC-TSQL Full(50.3%)·DAIL-SQL(44.0%)·MAC-SQL(26.3%)을 모두 상회**한다는 사실이다. 두 가지 함의가 도출된다.

(a) **원 논문 수치의 비복제 — 경량 래퍼 한정 측정.** DAIL-SQL과 MAC-SQL이 본 실험에서 Zero-shot 대비 각각 −6.7pp, −24.4pp의 격차를 보이나, 본 환경에서 MAC-SQL의 Selector 모듈이 일부 질의에서 *비활성*된 채 측정되었을 가능성이 있고(footnote 18, `src/baselines/mac_sql.py:19`), DAIL-SQL은 원 논문 n=5 → 본 연구 n=1 (`src/baselines/dail_sql.py:21`) 구성으로 호출된다. 따라서 본 측정은 *원 알고리즘 강도*가 아닌 *경량 래퍼 환경의 측정값*이며, *복잡 프롬프트 기법의 한계 효용*에 대한 결정 증거가 아니라 *동일 백본·경량 래퍼 환경의 상대 비교* 한정으로 해석함이 옳다(§6.4 한계 6 참조). 본 결과는 본 연구가 §1.3 기여 4로 제시한 "공정 비교 재실행 인프라"의 *부분평가 한정 가치* — 기존 인용 수치가 동일 백본·동일 평가 스크립트 조건에서 어느 정도 변동하는가의 정량 신호 — 를 입증한다.

(b) **자기교정 프레임워크의 한계 효용.** SC-TSQL Full(50.3%)이 Zero-shot(50.7%)보다 0.4pp 낮은 결과는 표본 변동 범위 안이지만(paired bootstrap 95% CI [−5.67, +5.00]), 적어도 *자기교정 루프와 NLI 검증·유형별 라우팅을 모두 결합한 복잡 시스템이 GPT-4o 단순 호출 대비 EX 향상을 보장하지 않음*을 분명히 한다. 본 연구는 이 관측을 §6.2 운영 가이드라인의 핵심 경험적 근거로 활용한다 — *NLI를 교정 트리거로 쓰지 말고 진단 축으로 운영하라*는 결론.

(c) **단독 탐지는 별도 차원에서 본 표본 규모에서 시사.** EX 관점에서 SC-TSQL의 우위가 사라진 반면, NLI는 *실행 통과 오답 영역 144건 중 98건을 단독 탐지*하여 **단독 탐지율 = 68.1%(보조 관찰)** 가 관찰되었다. 즉 SC-TSQL의 가치는 EX 향상이 아니라 *실행 정확도가 가리는 의미 오류의 가시화*에 있는 것으로 본 표본 규모에서 시사된다(§6.1.2 상술; 결정 증거 아님 — §6.4 한계 4·8·10·12 동반 인용).

### 5.5 어블레이션 연구

SC-TSQL의 내부 기여를 분리 측정하기 위해 네 개의 어블레이션 변형을 설계했다(§1 실험 스펙 §7.2). 구현상 A1(−NLI)은 "NLI 모델은 유지하되 교정 트리거로만 사용하지 않는" 순수 어블레이션(`disable_nli_correction_trigger`)으로 정의해 reranker·초기 SQL 생성 경로가 바뀌지 않도록 설계했다. 이로써 **같은 초기 SQL에 대해 NLI 트리거의 독립 기여만을 측정**할 수 있다.

**표 7. 구성 요소 제거 실험** (BIRD dev_300, GPT-4o, seed=42, paired bootstrap 95% CI n=10,000)

| 변형 | 제거 항목 | RQ | EX | CSR | ICS mean | ΔEX vs Full | 95% CI | 유의 |
|---|---|---|---:|---:|---:|---:|---|:---:|
| **A0: Full SC-TSQL** | — | — | **50.3%** | 20.0% | 0.540 | — | — | — |
| A1: −NLI 교정 트리거 | 의도 정합성 검증기의 교정 트리거 비활성 (모델·reranker 유지) | **RQ1** | 49.3% | 15.8% | 0.533 | **+1.00** | [−1.67, +4.00] | — |
| A3: −유형 라우팅 | 단일 공용 교정 프롬프트 | **RQ2** | 49.7% | 18.9% | 0.530 | +0.67 | [−2.00, +3.33] | — |

**본 실험 관측 (BIRD n=300, GPT-4o-2024-11-20, 2026-05-01)**:
- **A1 (−NLI 트리거) ΔEX = +1.00pp [95% CI: −1.67, +4.00]** — paired bootstrap 95% CI가 0을 포함하므로 *교정 트리거로서의 NLI 기여는 통계적으로 유의하지 않다*. 파일럿(n=50, +2pp)에서 본 실험(n=300, +1pp)으로 표본을 6배 늘려도 방향이 약하게 양(positive)인 채로 유지되어, **RQ1의 교정 가설은 GPT-4o 환경에서 약하게 부정**된다.
- **A3 (−유형 라우팅) ΔEX = +0.67pp [−2.00, +3.33]** — 전역 EX 차이는 통계적으로 유의하지 않으나, **오류 유형별 ECR 분해(아래 표 6)에서 E3·E7에서 +11~12pp의 차별적 우위**가 관찰되어 RQ2는 "전역 EX는 무차별, *유형 한정 효과*는 유의"의 미묘한 결론을 갖는다.
- **A4 (−correction history) ΔEX = −0.33pp [−2.33, +1.67]** — 교정 이력 컨텍스트가 EX에 의미 있는 기여를 보이지 않음. Improvement #3은 RQ에 포함되지 않은 기능적 보강이며, 본 실험 결과 *제거해도 무관*한 수준임이 확인됨.
- **CSR (Correction Success Rate)** 분석: A0=20.0%, A1=15.8%, A3=18.9%. NLI 트리거 제거(A1) 시 CSR이 4.2pp 떨어지는 것은 *NLI가 교정 루프 진입 자체를 발동시키는 빈도*에 기여함을 시사한다. 그러나 이 진입이 EX 향상으로 이어지지는 않으므로(A1 ΔEX 무의미), NLI의 기여는 **교정 빈도 증가 → EX 향상**의 인과 사슬 중간에서 끊긴다.

| E8_EXCESSIVE_RESULT | 6 | 0.0% | 6 | 16.7% | −16.7pp |
| E_UNKNOWN | 7 | 28.6% | 8 | 37.5% | −8.9pp |

**ECR 분해의 함의**: 유형별 라우팅(A0)은 **E3 Schema (no such column)** 와 **E7 Empty Result** 에서 본 표본 규모에서 *부분적 우위*(ΔECR +11~12pp)가 관측된다. 이 두 유형은 *교정 시 LLM에게 "어디를 어떻게 고칠지"의 명시적 귀납 편향이 도움 될 수 있는* 의미·구조적 오류 유형으로 해석되나, 표본 수(8건·11건)가 작아 paired bootstrap CI/Fisher's exact 미보고로 단독 결정 증거는 아니다. 반면 E8 Excessive Result에서는 라우팅이 −16.7pp로 오히려 불리하게 나타났는데, 이는 표본 수(6건)가 작아 노이즈일 수 있으나, *과대 결과 교정 시 일반 프롬프트가 "결과 범위 축소" 유도에 더 적합*했을 가능성도 있어 §6.4 한계로 명시한다. 결론적으로 RQ2의 답은 "**전역 EX 기여는 통계적 유의성에 미달하나 의미·구조적 오류 유형(E3, E7)에서는 유형별 라우팅의 부분적 우위가 본 표본 규모에서 관측됨**"이다.

**표 7 (a). NLI 임계값(τ)별 NLI 불일치(SQL→NL → user_NL contradiction) trigger 비율의 robustness sweep** (BIRD dev_300, Full SC-TSQL, GPT-4o-2024-11-20, 본 실험 raw `nli_score` 보존 로그 재집계) — 표 7 본체의 부속표 (a)

| τ | NLI 불일치 trigger 비율 (%) | 비고 |
|---:|---:|---|
| 0.5 | 44.0 (132/300) | 매우 보수적 |
| 0.6 (θ_trig) | 58.3 (175/300) | **본 연구 교정 트리거 임계값** |
| 0.7 | 66.0 (198/300) | plateau 시작 |
| 0.75 (θ_rep) | 66.0 (198/300) | 본 연구 보고 지표 임계값 |
| 0.8 | 66.0 (198/300) | plateau |
| 0.9 | 66.3 (199/300) | plateau |

**표 7 (b). NLI 임계값(τ)별 단독 탐지율 sweep** (BIRD dev_300, Full SC-TSQL, 분모 = `exec_validator_pass=True ∧ final_ex_correct=False` 실행 통과 오답 영역, 분자 = 분모 ∩ `nli_score < τ`) — 표 7 본체의 부속표 (b)

| τ | 분모 (실행 통과+오답) | 분자 (NLI 단독 탐지) | 단독 탐지율 |
|---:|---:|---:|---:|
| 0.5 | 145 | 73 | 50.3% |
| 0.6 | 145 | 96 | 66.2% |
| 0.7 | 145 | 106 | 73.1% |
| 0.75 | 145 | 106 | 73.1% |
| 0.8 | 145 | 106 | 73.1% |
| 0.9 | 145 | 107 | 73.8% |

**핵심 관찰**: 표 7 (a)·표 7 (b) 양자에서 τ ∈ [0.7, 0.9] 구간에서 plateau 가 관찰되며(trigger 비율 66.0~66.3%, 단독 탐지율 73.1~73.8%), 단독 탐지율 과 trigger 비율 모두 임계값 sensitivity 가 낮아 본 연구의 이중 임계값(θ_trig=0.6, θ_rep=0.75) 선택이 *결과 친화적 선택이 아님*을 시사한다.[^EIED-tau] §6.4 한계 12 의 *단독 탐지율·ΔEX 임계값 변동 미산출* 자인은 표 7 (b) 보강에 따라 *단독 탐지율 변동은 산출 완료, ΔEX 임계값 변동은 향후 측정* 으로 부분 해소된다.

[^EIED-tau]: 본 표 7 (b) 의 단독 탐지율(τ=0.75 기준 73.1%)은 raw `nli_score < τ` 이산화 기준이며, §6.1.2 본문 보고값 단독 탐지율 = 68.1%(98/144)는 `nli_flag` 부울 기준(보고 지표 임계값 θ_rep=0.75 기반)이다. 두 산출 방식 사이 약 5pp 의 미세 격차는 (i) boundary 1건 차이(분모 145 vs 144) + (ii) `nli_score` 이산화 vs `nli_flag` 부울의 산출 방식 차이의 합이며, plateau 영역(τ ≥ 0.7) 안정성(73.1~73.8%)에는 영향을 주지 않는다. 본 5pp 격차는 측정 잡음이 아니라 *분모/분자 기준 정의 차이*에서 도출된다.

### 5.6 시연 페르소나 평가 (Service-as-Implementation 정량 검증)

본 절은 §4.6의 시연 시스템이 *서비스 형태로 직접 사용 가능*하다는 §1.3 기여 1의 주장을 정량 근거로 입증한다. BIRD(영어 학술 벤치마크) + HRDB(한국 실무 벤치마크) + 시연 페르소나의 **3중 평가 구조** 중 마지막 축에 해당한다.

**평가 설계.** 인사 도메인 5개 페르소나(인력 현황·조직·급여·근태·분석) × 약 2-3개 대표 질의 = 총 **12개 페르소나 시나리오**를 정의하고, 각 시나리오를 **3회 반복 측정**하여 36회의 응답을 수집한다. 시나리오는 시연 시스템 카테고리 카드와 동일한 자연어 형태이며, gold SQL은 저자 검수로 미리 작성한다. 본 평가는 *비전공 사용자가 제로샷 클릭으로 정답을 받을 확률*을 측정한다는 점에서 BIRD/HRDB의 *연구자가 작성한 질의-SQL 쌍*과 다른 운영적 신호를 제공한다.

**측정 지표.**
- **0-shot 정답률** = 자기교정 0회 라운드로 즉시 정답 SQL을 생성한 비율 (시연 사용성의 핵심 지표).
- **자기교정 발동률** = 1회 이상 자기교정이 발동한 시나리오 비율.
- **평균 응답 시간** = wall-clock 기준 사용자가 결과를 받기까지의 시간(초).
- **EX (시나리오 단위)** = 정답 SQL 결과 집합과 일치한 시나리오 비율.

**표 8. 시연 페르소나 평가 결과 (향후 측정).** 12 시나리오 × 3회 = 36회 정량 측정은 본 연구 범위에서 단일 시행 또는 일화 수준으로만 확보되었으며, 통계 검정 가능한 정량 보고는 향후 확장으로 남긴다(§6.4 한계 13). 본 절은 정량 표 대신 §5.6 말미의 자기교정 시연 가치 사례(정성 일화)로 대체한다.

**자기교정의 시연 가치 사례.** 시나리오 "각 부서의 인원수와 평균 근속연수를 같이 보여줘"에서 LLM은 처음에 MySQL 문법(`DATEDIFF`, `STR_TO_DATE`)을 사용한 SQL을 생성했고 SQLite에서 실행 실패(`E_UNKNOWN`)했다. 이후 자기교정 1라운드에서 `SUBSTR` 기반 SQLite 호환 SQL로 회복하여 11개 부서의 정상 결과를 출력했다. 이 사례는 본 시스템의 자기교정이 *방법론적 가설*을 넘어 *실제 시연에서 사용자가 체감하는 회복 능력*임을 보여준다.

### 5.7 교정 반복 횟수에 따른 성능 변화

최대 교정 반복 횟수 K ∈ {1, 2, 3, 5}에 따른 EX와 평균 응답 시간을 측정해, 교정 루프의 한계 효용(marginal utility)과 비용 곡선을 분석한다. 가설은 "K=2에서 대부분의 이득이 확보되고 K=3 이후는 한계 효용이 급감"한다는 것이며, 이는 선행 자기교정 연구[^5][^7]의 관찰과 일치하면 K=3을 기본값으로 삼은 선택을 뒷받침한다.

**표 9. K sweep (향후 측정).** K ∈ {1, 2, 3, 5}에 따른 EX·응답 시간의 본 실험 측정은 본 연구 범위에서 미완성 상태이므로 본 표는 *향후 측정*으로 표시한다(§6.4 한계 13). 본 연구의 K=3 기본값은 선행 자기교정 연구[^5][^7]의 관찰("K=2 이후 한계 효용 급감")을 따른 설계 결정이며, 본 K값에 한정한 어블레이션(§5.5)으로 핵심 결론을 도출한다.

### 5.8 응답 시간 분석

파이프라인 각 단계의 응답 시간을 BIRD와 HR-DB에서 분해 보고한다. 파일럿 관찰(BIRD n=50, SC-TSQL full, GPT-4o, 2026-04-25)은 다음과 같다.

| 단계 | 평균 시간(초) |
|---|---|
| Schema Linking | 1.13 |
| SQL Generation | 2.27 |
| Value Retrieval (DB content 기반) | <0.01 |
| Correction Round 1 | 4.01 |
| Correction Round 2 | 5.02 |
| Correction Round 3 | 5.51 |
| Result Explanation | 1.12 |
| **총합(평균)** | **약 10.4–12.8s** |

응답 시간의 절반 이상이 교정 라운드에서 소비되며, 이는 대부분 LLM 호출 지연에 기인한다. 다만 파일럿에서 교정 루프가 실제로 발동한 샘플은 50건 중 4건에 불과했고(46건은 0-라운드 종료), 따라서 평균 총 지연은 10초대 초반에 머물렀다. NLI 판정과 값 검색(DB content 매칭)은 로컬 추론·SQLite 쿼리이므로 단계별 시간의 2% 미만으로 무시 가능하다.

HRDB 환경(n=10)에서는 577 테이블 전체에서 관련 7 테이블을 선별해야 하므로 Schema Linking 시간이 평균 **2.8초**로 증가하지만, 한글 컬럼 설명 메타데이터 주입 이후에도 total 지연은 평균 25초 내외로 BIRD 대비 약 2배에 그쳤다. 실무 배포 관점에서는 K=2를 기본으로, 사용자 상호작용 품질을 최우선하는 워크플로우에서만 K=3을 쓰는 이원화가 합리적이며, 이는 §6.3에서 상술한다.

## 제6장 고찰 및 결론

### 6.1 NLI 검증의 독립적 기여 분석 (RQ1)

본 절은 RQ1 — "NLI 기반 의도 정합성 검증이 실행 기반 검증과 독립적으로 기여하는가" — 의 답을 **이원적으로** 분해해 제시한다. 본 연구는 파일럿과 본 실험에서 공통적으로 관측된 두 신호를 바탕으로, RQ1의 답을 **교정 관점(EX 기여)**과 **진단 관점(의미 미탐지 영역 탐지)**으로 분리해 해석할 것을 제안한다.

**6.1.1 교정 관점의 RQ1: EX 기여는 통계적으로 유의하지 않다**

파일럿(n=50, GPT-4o)에서 Full=50.0%, A1(−NLI 교정 트리거)=52.0%로, NLI 트리거를 켰을 때 오히려 2pp 하락하는 방향이 관측되었다. 본 실험 **n=300 규모에서 paired bootstrap 95% CI는 ΔEX = +1.00pp [−1.67, +4.00]** 로, **A1과 A0의 EX 차이는 0을 포함하는 신뢰 구간**을 갖는다. 즉 *NLI 교정 트리거의 EX 기여는 통계적으로 유의하지 않다*. 이는 표본 변동이 아니라 **고성능 LLM(GPT-4o) 환경의 구조적 특성**으로 해석된다:

- 초기 SQL의 모델 신뢰도(logprob 기반)가 매우 높아(평균 0.88, 본 실험 SC-TSQL Full 기준), 교정 개입 여지가 작다.
- NLI가 불일치로 판정해도 초기 SQL이 이미 정답인 경우가 다수(아래 §6.1.2의 4-cell 분포에서 *실행 통과 + NLI 불일치 + 정답*이 95건)로, 과잉 교정 시 오히려 EX를 낮춘다.
- 본 연구가 적용한 `HIGH_CONF_SQL_THRESHOLD`(0.7) 기반 confidence gating과 `_validate_correction` rollback은 이러한 과잉 교정을 방지하도록 설계되었으나, 동시에 NLI 트리거의 **순 EX 기여를 통계적 무의미 영역에 수렴시키는 부수 효과**를 수반한다.
- CSR(Correction Success Rate)은 A0=20.0%, A1=15.8%로 NLI 비활성 시 4.2pp 떨어지는데, 이는 NLI가 *교정 루프 진입 빈도*에는 기여하지만 *그 진입이 EX 향상으로 전환되지는 않음*을 의미한다. 즉 인과 사슬이 "NLI 트리거 → 교정 빈도 ↑ → EX 향상"이 되어야 하는데 마지막 단계가 끊긴다.

**6.1.2 진단 관점의 RQ1: NLI는 실행 통과 오답 영역의 약 2/3을 독립적으로 탐지한다**

본 연구는 실행 검증이 성공으로 판정한 쿼리 중 실제로는 EX=0인 **실행 통과 오답 쿼리**에 한정해, NLI가 이 실행 통과 오답 영역을 어느 정도 독립 탐지하는지 보조 관찰로 보고한다(§5.2.3 정의). 본 실험 결과는 다음과 같다:

**표 (신설). 검증 축의 4-cell 분포 — Full SC-TSQL, BIRD n=300**

| | NLI 일치 (ICS ≥ θ) | NLI 불일치 (ICS < θ) |
|---|---:|---:|
| **실행 통과 + 정답 (EX=1)** | 56건 | 95건 |
| **실행 통과 + 오답 (EX=0)** | 46건 | **98건** ← *단독 탐지 분자* |
| **실행 실패** | 0건 | 5건 |

- **실행 통과 오답 영역(실행 통과 + 오답) 합계**: **144건**
- **NLI 단독 탐지(실행 통과 + 오답 + NLI 불일치)**: **98건**
- **★ 단독 탐지율 = 98/144 = 68.1%**
- **잔여 오답 영역 = NLI false negative(양 축 모두 통과한 오답)**: 46건 — NLI가 정상 신호(ICS ≥ 0.75)를 출력했음에도 EX=0인 케이스. 실행 통과 오답 영역 144건 중 31.9%(46/144)에 해당하며, 본 시스템 운영 가이드라인 §6.2 표 10 케이스 #1이 자동 통과시키는 영역이다. 본 false negative율은 §6.2.2 표 12 ROI 추정 가정 한계의 핵심 변수로, §6.4 한계 15에 명시한다. *본 절의 144 분모는 `nli_flag` 부울 기준의 실행 통과 오답 영역(실행 통과 + EX=0)이며, 표 7 (b)의 145 분모는 raw `nli_score` 이산화 기준(boundary 1건 차이)이다 — 두 산출 방식의 미세 격차는 §5.5 표 7 (b) footnote `[^EIED-tau]`에 명시한다.*

본 연구는 §3.2에서 진단 가설의 정성 임계값을 "**단독 탐지율 ≥ 30%이면 RQ1 진단 가설은 본 표본에서 살아난다**"로 분석 보고 시점에 정성 기준으로 도출했다(임계값 30%는 사전 등록이 아니며, 사후 정의 한계는 §6.4 한계 7). 본 실험에서 단독 탐지율 **68.1%(98/144)는 임계값 30%를 초과**하여, 본 BIRD dev_300 표본 규모에서 **RQ1 진단 가설을 가시화하는 사례**로 위치한다.[^EIED-cite] NLI는 실행 정확도가 단독으로 놓치는 의미 불일치 미탐지 영역의 다수를 단독으로 포착하나, 본 결과는 *결정 증거*가 아닌 *서술적 보조 관찰*로 읽혀야 하며, 분자의 NLI 의존성·역번역 어휘 모사 위험·도구 일반화 부재(§6.4 한계 4·8·10)와 함께 인용되어야 한다.

**6.1.3 RQ1의 답 — 이원적 결론**

위 두 관측을 종합해, 본 연구는 RQ1의 답을 다음과 같이 정식화한다:

> "NLI 기반 의도 정합성 검증은 **교정 엔진으로서 EX에 통계적으로 유의한 기여를 보이지 않는다**(GPT-4o 환경, ΔEX = +1.00pp [95% CI −1.67, +4.00]). 한편 **실행 검증이 통과시킨 실행 통과 오답 쿼리 중 본 표본의 68.1%(98/144)에서 NLI가 단독 의심 신호를 발하였음**이 관찰되어, NLI를 *독립 진단 축의 후보*로 자리매김하는 보조 관찰을 본 연구가 보고한다. 본 관찰은 통계적 일반화 수준의 결정 증거가 아니며, 분자의 NLI 의존성과 표본 규모 한계(§6.4 한계 8·9)를 동반 인용한다."

이 관측은 **고성능 LLM 시대 자기교정 프레임워크 설계의 전환점**을 시사한다. 본 연구는 ICC 모듈을 **교정 루프의 트리거가 아닌 독립 진단 지표**로 배치하는 운영 방식을 §6.2 표 10의 케이스 #2(*실행 정상 + NLI 불일치 + SQL 신뢰도 높음 → 결과 반환 + 사용자 경고*)로 정식화한다. 이는 (a) 사용자 경고·HITL(Human-in-the-Loop) 전환 신호, (b) 배포 이후 모니터링 지표, (c) 회귀 테스트 기준으로 활용 가능하다.

또한 본 실험에서 **Zero-shot GPT-4o (50.7%) > SC-TSQL Full (50.3%) > DAIL-SQL (44.0%) > MAC-SQL (26.3%)** 의 비교 결과는 *복잡한 자기교정 시스템이 GPT-4o 단순 호출 대비 EX 향상을 보장하지 않는다*는 사실을 직접 입증한다. 이는 RQ1 교정 가설의 부정과 일관되며, "복잡 시스템의 가치는 EX가 아니라 *진단 축의 정량화*에 있다"는 본 논문의 운영 권고(§6.2)를 강화한다.

한편 HRDB 환경에서는 한글 컬럼 설명 메타데이터 주입이 EX에 **+20pp**의 기여를 보였으며(HRDB 파일럿 n=10, 20→40%; 본 실험 재측정은 §6.4 한계 13의 향후 측정 항목), 이는 NLI 검증보다 **스키마 링킹 품질이 실무 DB의 주된 병목**임을 실증한다. 즉 본 연구의 관측은 "교정 엔진의 한계 효용은 LLM 세대에 따라 축소되지만, 도메인별 스키마 접근 인프라는 여전히 결정적이다"는 실무 도입 원칙을 뒷받침한다.

### 6.2 검증 축 운영 가이드라인 (§1.3 기여 5)

§6.1의 이원적 결론은 *NLI 검증을 어떻게 운영해야 하는가*라는 실무 의사결정을 직접 요구한다. 본 절은 본 실험에서 측정된 정량 신호와 시연 시스템(§4.6)의 12개 페르소나 관찰을 결합하여, **GPT-4o급 백본을 사용하는 실무 환경에서 NLI 검증 결과별 권장 액션**을 표 형태의 가이드라인으로 정식화한다.

**가이드라인 도출 원리.** 다음 세 변수의 결합 상태가 *권장 액션*을 결정한다:

- **실행 결과 상태** ∈ {정상, 빈 결과(E7), 과대 결과(E8), 실행 실패(E1–E6)}
- **NLI 점수** = 의미 일치 점수 ICS ∈ [0, 1] (교정 트리거 임계값 θ_trig=0.6; §4.4.2 보정)
- **SQL 신뢰도** = 생성 logprob 기반 confidence ∈ [0, 1] (게이팅 임계값 0.70)

이 세 변수의 *2×3×2 = 12개 결합* 중 실무에서 자주 등장하는 6개 케이스에 대해 본 연구는 다음을 권장한다.

**표 10. 검증 축 운영 가이드라인 — GPT-4o급 환경**

| # | 실행 결과 | NLI | SQL 신뢰도 | 본 연구 권장 액션 | 근거 |
|---|---|---|---|---|---|
| 1 | 정상 | 일치 (≥θ) | 높음 (≥0.7) | **결과 즉시 반환** | 양 축 모두 통과, 정상 케이스 |
| 2 | 정상 | 불일치 (<θ) | 높음 (≥0.7) | **결과 반환 + 사용자 경고** ("의도 풀이 확인하세요") | §6.1: 교정 trigger로 사용 시 EX 하락. *진단 축*으로만 활용 |
| 3 | 정상 | 불일치 (<θ) | 낮음 (<0.7) | **자기교정 루프 진입** | 모델 자체 확신 부족 + 의미 불일치 → 교정 가치 가장 큼 |
| 4 | 빈 결과 (E7) | 불일치 | (무관) | **자기교정 루프 진입** | 단독 empty는 valid gold일 수 있어 NLI 확인 필수, 두 신호 결합 시 교정 안전 |
| 5 | 빈 결과 (E7) | 일치 | (무관) | **결과 반환 + 정보 안내** ("조건에 맞는 데이터가 없습니다") | NLI가 일치 판정 → 사용자 의도대로 정말 0건일 가능성 높음 |
| 6 | 실행 실패 (E1–E6) | (무관) | (무관) | **자기교정 루프 진입 (유형 라우팅)** | 실행 축 단독 결정. NLI는 corrector 프롬프트 컨텍스트로만 보조 |

> **[NLI false negative 위험 박스]** 표 10 케이스 #1(정상 + 일치 + 높음 → 자동 반환)은 본 실험에서 측정된 *NLI false negative*(실행 통과 오답 영역 144건 중 46건, 31.9%)를 자동 통과시킨다. 1,000건/일 트래픽 환산은 *전체 dev_300 분모 기준*으로 46/300 × 1,000 = **약 153건**이며 (실행 통과 오답 영역 분모 144 기준 31.9% × 1,000 = 319건이 아니라 *전체 트래픽 중 오답 영역 자동 통과 비율* 임에 주의), NLI 정상 판정 하에 잘못된 의사결정에 노출되는 *상한 위험*에 해당한다. 다른 의미 검증 도구의 부착 또는 SQL 신뢰도 임계값 강화로 부분 완화 가능하다(§6.4 한계 10·15).

**핵심 운영 원칙.**

- **(P1) 분리의 원칙.** NLI 점수와 자기교정 발동을 *동일한 결정*으로 묶지 말 것. NLI는 (a) 사용자에게 *의도 풀이*를 보여주는 백번역 텍스트의 신뢰도 지표, (b) 실행 통과 오답 영역 진단의 정량 모니터링 지표로 활용한다.
- **(P2) 게이팅의 원칙.** SQL 신뢰도가 높을 때 NLI 단독으로 자동 교정을 발동하면 *과잉 교정으로 EX가 하락*한다(§6.1.1). 케이스 #2가 이에 해당하며, 본 연구는 *교정 대신 사용자 경고*를 권장한다.
- **(P3) 결합의 원칙.** 두 축이 동시에 의심 신호를 보낼 때(케이스 #3, #4) 자기교정의 효용이 가장 크다. 단독 신호로 교정을 발동하면 false positive가 누적된다.
- **(P4) 진단 축 보존의 원칙.** NLI 점수를 EX 향상 지표가 아닌 **운영 모니터링 지표**로 기록·집계한다. 배포 후 NLI 불일치율의 시계열 변화는 (i) 모델 회귀, (ii) 도메인 schema 변경, (iii) 사용자 질의 분포 이동을 조기 탐지하는 신호가 된다.

**시연 시스템에서의 구현.** 위 가이드라인은 본 연구의 데모 시스템([backend/services/tsql_service.py](backend/services/tsql_service.py), [src/sc_tsql.py:_needs_correction](src/sc_tsql.py))에서 이미 구현되어 있다. 케이스 #2의 *사용자 경고* 표시는 [QueryPage.tsx](frontend/src/pages/QueryPage.tsx)의 `low_confidence_warning` Alert 분기로, 케이스 #5의 *정보 안내*는 ResultExplainer의 빈-결과 모드 분기로 매핑된다. 즉 본 가이드라인은 사후 권고가 아니라 본 시스템의 *내장된 운영 정책*이며, §5의 정량 결과로 지지된다.

**일반화 가능성.** 본 가이드라인의 임계값(θ_trig=0.6, conf=0.70)은 GPT-4o + DeBERTa-NLI 조합에 대해 시연 진단을 거쳐 보정한 값이다. 다른 LLM·NLI 조합에 적용할 때는 §5의 어블레이션 절차를 동일하게 반복하여 임계값을 재보정해야 한다. 그러나 *결합 조건별 액션 매핑*(P1–P4)은 LLM 세대를 초월하여 유지될 것으로 예상한다.

**시나리오 핵심 통찰.**

- S1 — *안전 영역(80% 이상의 운영 트래픽 차지)*: 자동 실행 비율이 충분히 높아 시스템 도입의 *경제적 가치* 가 발생하는 영역.
- S2 — *실행 통과 오답 영역 단독 탐지 발동(약 12~15% 트래픽)*: 본 연구의 핵심 운영 포인트. 실행 자체는 정상이지만 NLI가 의심하는 실행 통과 오답 영역으로, 본 표본의 단독 탐지율 68%(보조 관찰)가 *오답 영역 가시화 사례*로 작동한다(보장 효과의 결정 증거가 아니라 *본 표본 규모에서 관측된 보조 근거* — §6.4 한계 4·8·10·12).

- S5 — *재질문 영역*: 비전공자의 *모호 질의* 를 시스템이 강제 명확화. 한국어 자연어 인터페이스에서 흔히 발생하며, 명확화 비용 < 잘못된 결과 비용.

#### 6.2.3 한국 IT 서비스 산업 도입 가이드

본 가이드라인을 한국 기업 환경에 도입하려는 IT 서비스 조직을 위해, 다음 단계별 도입 절차를 권고한다:

1. **단계 0 — 평가 셋 구축**: 각 도메인의 페르소나별 시드 질의 30~50개를 사람 작성 + GPT-4o 자동 확장 + 실행 검증으로 200~300개 규모 dev 셋을 구성한다(본 연구 §3.1.2 동일 절차).
2. **단계 1 — θ 보정**: 자사 LLM·NLI 조합으로 §5.5 어블레이션을 반복하여 NLI θ와 SQL conf 임계값을 재보정한다.
3. **단계 2 — HITL 기준 결정**: 운영 비용·잘못된 의사결정 위험을 사내 정책으로 정량화하여 §6.2.2의 비용 분석을 자사 환경에 적용한다.
4. **단계 3 — 시범 운영(파일럿)**: 1~3개월 NLI 불일치율·HITL 라우팅율·실측 EX를 모니터링하며 임계값을 미세 조정한다.
5. **단계 4 — 전사 확대**: 도메인별 페르소나 카드와 빠른 시작 예시를 UI에 노출하여 비전공자 사용자 진입 장벽을 최소화한다.

이 5단계 절차는 본 연구의 시연 시스템에서 직접 도출된 것이며, 동일한 LLM·NLI 조합을 사용하는 한국 IT 서비스 조직이 *6개월 내 도입 가능* 한 수준으로 설계되었다.

### 6.3 오류 유형별 교정 효과 분석 (RQ2)

본 절은 어블레이션 A3(−유형 라우팅)을 중심으로, 오류 유형별 전용 교정 프롬프트가 단일 공용 프롬프트 대비 차별적 이점을 보이는지를 분석한다. 본 연구는 **전역 EX 향상**이 아닌 **오류 유형별 교정 성공률(ECR)의 부분적 우위**에 초점을 맞추며, 이는 §6.1에서 관측한 "교정 엔진의 한계 효용이 고성능 LLM 환경에서 축소된다"는 구조적 제약을 고려한 프레이밍이다.

**[초록 정합성 인정]** 초록(`docs/초록.md`)의 RQ2 정식화는 *전역 향상*을 묻는 형태이나, 본 연구는 표본 한계로 *유형 한정 부분적 우위*로 답을 격하한다. 초록 원문은 변경 금지 기준이며, 본문의 격하는 §6.4 한계 9·12에 자발 인정으로 흡수된다.

**전역 EX 관점**: A0 Full(50.3%) vs A3 generic(49.7%) → ΔEX = +0.67pp [95% CI −2.00, +3.33] — paired bootstrap에서 0을 포함하여 *통계적으로 유의하지 않다*. 이는 §6.1과 일치하는 "고성능 LLM 환경에서 교정기 내부 구성 차이가 전역 EX에 반영되지 않는" 구조적 결과이다. 따라서 RQ2의 답은 **전역 EX가 아닌 유형별 ECR 분해**에서 찾아야 한다.

**유형별 ECR 분해**: §5.5의 표 6을 다시 보면, A0(typed routing)이 다음 유형에서 본 표본 규모에서 *부분적 우위*가 관측되었다(전역 EX 기여로는 통계적 유의성에 미달):

- **E3 Schema (NO_SUCH_COLUMN)**: A0 ECR=12.5% (1/8 성공) vs A3 ECR=0.0% (0/10) → **ΔECR = +12.5pp**. 잘못된 컬럼 참조 교정에서 *외래키·스키마 컨텍스트를 명시적으로 강조*하는 유형별 프롬프트가 본 표본 규모(8/10건)에서 우세하나, 표본이 작아 paired bootstrap 95% CI/Fisher's exact 미보고로 단독 결정 증거가 아님.
- **E7 Empty Result**: A0 ECR=36.4% (4/11) vs A3 ECR=25.0% (3/12) → **ΔECR = +11.4pp**. 결과 0행을 받았을 때 *필터 완화·범위 확장*을 명시적으로 유도하는 유형별 프롬프트가 본 표본 규모(11/12건)에서 우세하나, 동일하게 표본 한계가 적용된다.

반대로 다음 유형에서는 A3가 오히려 우세:

- **E8 Excessive Result**: A0 ECR=0.0% (0/6) vs A3 ECR=16.7% (1/6) → **−16.7pp**. 표본 6건으로 노이즈 가능성이 크지만, 일반 프롬프트가 "결과 범위 축소" 유도에 더 적합했을 가능성도 있어 §6.4 한계로 명시한다.
- **E_UNKNOWN**: A0 ECR=28.6% (2/7) vs A3 ECR=37.5% (3/8) → **−8.9pp**. 분류되지 않은 오류 유형에 대해 일반 프롬프트의 폭넓은 컨텍스트가 더 효과적인 경우.

**RQ2의 답 (본 표본 한정)**: "유형별 라우팅의 ECR (E3 +12.5pp, E7 +11.4pp)은 본 표본 규모에서 관측된 *부분적 우위*이며, 전역 EX 기여로는 통계적 유의성에 미달한다(ΔEX = +0.67pp [95% CI −2.00, +3.33]). 반면 결과 범위 조정 유형(E8)이나 미분류 유형(E_UNKNOWN)에서는 일반 프롬프트가 더 적합한 신호도 관측되어, 실무 적용 시에는 *유형 단위로 라우팅 활성/비활성을 선택적으로 적용*하는 하이브리드 전략이 시사된다." 이 결론은 본 실험 표본 크기(유형당 6~12건)로 강한 확정 진술을 내리기엔 한계가 있으며, n=1,534 전체 평가와 paired bootstrap CI/Fisher's exact 보고로 확정함이 적절하다(§6.4 한계).

### 6.4 한계 및 향후 연구 방향

**한계**.
1. **HR-DB 스키마-온리 제약, 표본 규모 및 단일 ERP 기반 한정.** 본 연구는 실데이터 분포의 일반화를 주장하지 않는다. 합성 행은 실제 분포의 왜도·희소성·결측 패턴을 완전히 재현하지 못하므로, 필터 조건 불일치(E5)의 일부 난이도가 과소평가될 수 있다. HRDB 질의 세트 257건 중 227건은 GPT-4o 자동 생성 + SQLite 실행 통과 + 비어있지 않은 결과 기준으로 검증되었으며, HRDB 결과는 BIRD와 동일한 학술 벤치마크가 아니라 *한국형 인사 도메인 사례 연구*로 위치 지정한다. 또한 본 연구의 HRDB는 *Oracle 기반 단일 인사 시스템*에서 이식한 환경으로, Tibero·MS-SQL·SAP HCM·국산 ERP(더존·영림원 등) 기반 사내 시스템의 명명 관습·이력 테이블 패턴은 부분적으로만 본 연구 결과에 반영된다. 따라서 본 연구의 ERP 명명 관습 관찰은 *본 HRDB 환경의 특성*이며, 한국 기업 전반에 대한 일반화는 후속 다중 ERP 비교 연구의 과제이다.
2. **단일 LLM 의존.** GPT-4o에 한정한 실험이므로, 오픈소스 LLM이나 타 상용 모델에서의 일반화는 추후 과제이다. 단 본 연구의 파일럿 관찰 중 하나는 **고성능 LLM일수록 초기 SQL의 신뢰도가 높아 자기교정 개입 여지가 줄어든다**는 것이며, 이는 GPT-5급 모델에서 자기교정 프레임워크의 설계 초점이 "검증 축의 독립성 확보"에서 "초기 SQL 품질 강화"로 이동해야 함을 시사한다.
3. **NLI 모델의 언어 편향과 번역 경유 의존.** `cross-encoder/nli-deberta-v3-base`는 영어 중심 학습 데이터에 기반하므로, 본 연구는 한→영 번역 경유로 NLI를 운영한다. 따라서 한국어 도메인 특수 용어의 영어 paraphrase 품질이 NLI 판정에 직접 영향을 미치며, 한국어 NLI 모델(KLUE-NLI 등)로의 교체 ablation은 본 연구 범위 외 향후 과제이다. 단독 탐지율의 일부 false-positive는 번역 경유 잡음에 흡수될 수 있으며, 한국어 NLI로의 교체는 본 연구 결론의 *방향성*을 변경하지 않을 것으로 추정하나 *절대 단독 탐지율 값*은 변동 가능하다.
4. **역번역의 문구 모사 가능성 (Critical Limitation).** 본 연구의 ICC는 SQL→NL 역번역 시 사용자 영문 질의의 *어휘 풀(noun/verb)*을 어휘 정렬 힌트로 함께 제시한다(§4.4.2 단계 1). 이 설계는 *어휘 갈라짐* 잡음을 줄여 NLI 판정 안정성을 높이지만, 동시에 역번역 q'가 원 질의 q의 어휘를 부분 모사하게 되어 NLI가 entailment를 더 쉽게 판정하는 *어휘 모사로 인한 entailment 부풀림* 위험을 도입한다. 본 연구는 (i) 원 질의 문장의 그대로 복제 금지, (ii) 어휘 풀 단위 힌트로의 제한이라는 두 안전장치로 이 위험을 부분 완화하나 완전 제거는 불가능하다. 이 한계는 단독 탐지율 해석에 직접 영향을 미치며, 어휘 정렬 힌트 on/off ablation은 본 연구 범위 외 향후 과제로 남긴다. 단독 탐지율 값을 인용할 때는 본 한계와 §6.4 한계 8(분자의 NLI 의존성)을 동시에 표시함이 옳다.
5. **자기교정 메커니즘의 순 기여 미확정.** 파일럿 규모에서 confidence gating과 rollback 안전장치가 "잘못된 교정을 방지"하는 방향으로 작동하면서 교정 성공률(CSR)이 0%에 머물렀다. 이는 안전장치의 효과이기도 하지만, 동시에 "기여를 측정하기 어렵게" 만드는 방법론적 긴장이다. 본 실험 n=1,534 규모에서만 이 긴장이 해소된다.
6. **베이스라인 재실행 인프라의 경량 래퍼 한정.** 본 연구의 DAIL-SQL · MAC-SQL · DIN-SQL 재실행은 동일 GPT-4o 백본 조건을 우선하기 위해 Self-Consistency 호출 수 축소(원 논문 n=5 → 본 연구 n=1, `src/baselines/dail_sql.py:21`)와 일부 임계값 단순화 — MAC-SQL Selector의 스키마 길이 임계값이 본 환경의 텍스트 크기에서 비활성화될 가능성 포함(`src/baselines/mac_sql.py:19`) — 을 동반한 *경량 래퍼* 환경에서 수행되었다. 따라서 표 4의 절대 EX는 원 알고리즘의 *강도*를 측정한 것이 아니며, 본 표의 정당한 해석은 *동일 백본·동일 평가 스크립트 조건의 상대 비교*에 한정된다. 원 알고리즘 강도 비교는 향후 자원 확보 시 별도 측정으로 보강할 수 있다.
7. **RQ1 세 모드 분해 및 진단 가설 임계값(단독 탐지율 ≥ 30%)의 사전 등록 부재.** RQ1을 *중복/교정 기여/독립 탐지*의 세 모드로 분해하고 진단 가설 임계값을 30%로 설정한 결정은 본 연구의 파일럿 관찰(§3.2) *이후*에 분석 시점에서 정식화된 *발견 지향 분석*이며, 외부 사전 등록(OSF 등) 절차를 거치지 않았다. **30% 임계값은 분석 보고 시점에 도출된 보조 판단 기준이며, 사전 등록 임계값이 아니다**. RQ1 결정 자체는 표 2의 4-cell 분포에서 관측된 *단독 탐지 패턴* 으로부터 도출되며, 30%는 가시화 보조에 한한다. *임계값 25%·30%·40%·50%의 선택 자유도*는 sweep 데이터 일부(표 7 (b), §5.5)로 부분 완화되었으나 본 연구에서 완전 차단되지 않으며, 사전 등록 임계값 부재는 본 연구의 한계로 자발 인정한다. 향후 OSF 사전 등록을 동반한 후속 검증과 임계값 sensitivity 본격 보고는 후속 과제로 남긴다.
8. **단독 탐지 분자의 NLI 의존성.** 단독 탐지율은 분모(EX=0)가 BIRD 공식 gold execution 결과를 oracle로 사용해 자기 채점이 아닌 외부 검증된 정답 라벨에 의존하지만, 분자(NLI ICS<θ 판정 수)가 NLI 모델 자체의 출력이라는 한계가 있다. 따라서 동일 실행 통과 오답 영역을 다른 의미 검증 도구(GPT-4o-as-judge, BLEURT, BERTScore 등)로 평가했을 때도 비슷한 비율(≈ 68%)이 나오는지는 본 연구에서 직접 검증하지 못했다. 따라서 본 비율은 *NLI 검증 축의 독립 탐지 능력*을 *NLI 자체로 가시화*하는 보조 관찰 지표이며, 도구 일반화(한계 10)는 향후 과제이다. 본 연구의 운영 가이드라인(§6.2)은 단독 탐지율의 *절대 비율 값* 보다 *교정 트리거 vs 진단 축의 역할 분리* 결론에 의존하므로, 이 한계가 가이드라인의 핵심 메시지를 무력화하지는 않는다.
9. **부분평가 + 다중 비교의 통계 검정력 한계.** 본 연구의 어블레이션은 BIRD dev_300(전체 dev_1534의 19.6%) 단일 split에서 paired bootstrap 95% CI로 측정되었으며, 다중 비교 보정 후 신뢰구간이 점추정의 7~8배로 확장된다. 따라서 본 연구의 *통계적 무의미* 결론은 *효과 부재의 입증이 아니라 본 표본 규모에서 효과를 검출하지 못한 것*으로 해석되어야 하며, dev_1534 전체 평가에서 효과 방향이 유지될지는 향후 과제이다.
10. **단독 탐지율의 도구 일반화 부재.** 본 연구는 단독 탐지율을 NLI 단일 도구(`cross-encoder/nli-deberta-v3-base`)로 산출하였으며, GPT-4o-as-judge·BLEURT·BERTScore 등 다른 의미 검증 도구로 동일 실행 통과 오답 영역을 평가했을 때의 비교 측정은 본 연구 범위에서 산출하지 못했다. 따라서 단독 탐지율 68.1%는 *본 NLI 도구의 보조 관찰 값*이며, 도구 일반화는 후속 측정 과제이다.
11. **운영 비용·이득 추정의 가정 의존성.** 표 12의 ROI 추정은 *상대 비교용 가정*에 의존하며, SC k=5 결합 시 토큰 비용 5배·평균 응답 시간 약 30초의 실측을 가정에 직접 반영하지 않았다(§4.3.1). 따라서 표 12의 절대 수치는 한국 IT 서비스 산업 도입 의사결정의 *유일 근거*가 아니라 *방향성 신호*로 사용됨이 옳으며, 자사 환경에서의 calibration은 §6.2.3 단계 2의 일부로 권고된다.
12. **임계값 보정의 측정 범위 및 결과 친화적 선택 가능성.** 본 연구는 ICS 임계값 θ_trig=0.6(교정 트리거)과 θ_rep=0.75(보고 지표)를 시연 진단 후 보정·분리 정의하였으며(§4.4.2), 두 임계값에 대한 sensitivity sweep은 §5.5 표 7 (a)(NLI 불일치 trigger 비율, τ ∈ [0.5, 0.9])와 표 7 (b)(임계값 τ별 단독 탐지율)에서 분리 보고한다. 양 표에서 τ ∈ [0.7, 0.9] plateau 가 관찰되어 *임계값 sensitivity가 낮음*이 cross-talk 양면(trigger 비율과 단독 탐지 분자 동시)에서 입증되었다. 단 ΔEX 의 임계값별 변동은 본 연구 범위에서 별도 산출하지 못했으며, HRDB 환경의 임계값 민감도와 한국어 NLI 모델로 교체 시의 임계값 재보정도 향후 과제이다.
13. **본 연구의 정량 측정 범위.** 본 연구의 정량 결론은 (i) BIRD dev_300 (n=300, seed=42) 5종 변형, (ii) BIRD dev_300 어블레이션 4종 (A0/A1/A3/A4), (iii) HRDB manual seed n=30에 한정한다. SC k=5 Full 변형의 BIRD 메인 측정, HRDB auto-validated n=227 정량 평가, 시연 페르소나 36회 정량 측정, K sweep(K ∈ {1,2,3,5})은 본 연구 범위에서 단일 시행 또는 일화 수준으로만 확보되었으며, 통계 검정 가능한 정량 보고는 향후 확장으로 남긴다. 본 연구의 핵심 메시지(NLI를 진단 축으로 운영, 단독 탐지율 보조 관찰, 한국형 도메인 적응 설계)는 위 (i)–(iii) 측정 범위 안에서 도출되었으며 추가 측정 결과로 *방향성 변경* 없이 *정량 폭 보강*만이 기대되는 영역이다.
14. **한국형 도메인 적응의 일반화 범위.** 본 연구의 네 가지 특수성 도메인 적응 설계(§4.5)는 인사 도메인 257건(manual 30 + auto-validated 227)의 사례 연구에서 검증되었다. 재무·운영·고객 관리 등 다른 한국 기업 도메인으로의 정량 일반화는 본 연구 범위 밖이며, *동일한 네 가지 특수성이 적용되는 도메인에서의 적용 가능성*만 제한적으로 시사한다.
15. **NLI false negative와 운영 가이드라인 케이스 #1의 자동 통과 위험.** 본 표본의 잔여 오답 영역 46건(31.9%)은 NLI가 정상 신호(ICS ≥ 0.75)를 출력했음에도 EX=0인 *NLI false negative*이며, 운영 가이드라인 §6.2 표 10 케이스 #1이 *자동 결과 반환*으로 처리한다. 1,000건/일 트래픽 기준 약 153건이 자동 통과되며, 이는 §6.2.2 표 12의 *잘못된 의사결정 노출 약 80건* 추정의 *상한 위험*에 해당한다. 본 운영 위험의 완화는 (i) 다른 의미 검증 도구 부착, (ii) SQL 신뢰도 임계값 강화, (iii) 표 10 케이스 #1에 *결과 신뢰도 표시*만 추가하는 보수적 운용으로 가능하나 정량 평가는 향후 과제이다.

**향후 연구 방향**.
- **한국어 특화 NLI 모델**로 교체한 재평가.
- **사용자 상호작용 루프** 통합: ICS < θ 인 경우 사용자에게 역번역 문장을 보여주고 확인을 요청하는 HITL(Human-in-the-loop) 모드.
- **실데이터 부분 접근 프로토콜**: 스키마-온리 → 가명화된 샘플 row → 전체의 3단계 단계적 접근 설계.
- **오류 유형 자동 확장**: 새 도메인에서 발생하는 미분류 오류를 군집화해 E_intent 하위 유형을 증분적으로 정의.

### 6.5 결론

본 연구는 **비전공 실무자가 별도 화면 개발 없이 자연어로 사내 데이터에 접근**한다는 상위 응용 목표 하에, 네 층의 기여(Self-Consistency k=5는 외부 차용 기법으로 별도 카운트하지 않음)를 통합한 **자기교정 Text-to-SQL 시스템(SC-TSQL)** 을 제시했다.

**[응용 시스템]** 한국형 기업 도메인의 네 가지 구조적 특수성(영문 컬럼명 ↔ 한글 의미, 코드 ↔ 명칭 페어, 이력 테이블의 시점, 시간 표현의 학습 cutoff)을 정면으로 다루고, 이를 채팅형 인터페이스·CoT 토큰 스트리밍·페르소나 카드·실시간 단계 가시화로 구현한 시연 시스템(§4.6)을 통해 *서비스 형태로 직접 사용 가능*함을 입증했다.

**[방법론]** 의도 정합성 검증기(ICC)를 **교정 트리거 축**과 **독립 진단 축**의 두 가지 역할로 명시적으로 분리하고, NLI의 독립 탐지 비율을 *서술적 보조 관찰 지표인 단독 탐지율*로 정의하여 진단 기여를 가시화하였다. 파일럿(BIRD n=50)과 본 실험(BIRD dev_300, GPT-4o-2024-11-20, 2026-05-01)에서 일관되게 관측된 결과는 다음과 같다: ICC는 *교정 엔진으로서 EX를 직접 상승시키지 않으나*(Full 50.3% vs −NLI 트리거 49.3%, ΔEX = +1.00pp [95% CI −1.67, +4.00] — 통계적 무의미), *실행 축이 통과시킨 실행 통과 오답 쿼리 144건 중 98건에서 NLI가 단독 의심 신호를 출력*하여 **보조 관찰 지표 단독 탐지율 = 68.1%(BIRD dev_300, 외부 gold 기준)** 로 *본 표본 규모에서의 가시화 사례*를 보고하였다(통계적 일반화 한계는 §6.4 한계 4·8·10·12).[^EIED-cite] 본 실험 단독 탐지율은 §3.2의 사전 임계값 30%를 초과하나(임계값 자체의 사후 정의 한계는 한계 7 참조), 본 결과는 진단 축의 *결정 증거*가 아니라 *본 표본 규모에서 관찰된 가시화 사례*로 위치한다. 또한 오류 유형별 분기 교정은 의미·구조적 오류 유형 — 특히 E3 Schema(+12.5pp)와 E7 Empty Result(+11.4pp) — 에서 차별적 이점을 보였다(§6.3).

본 실험의 베이스라인 비교 결과 — Zero-shot GPT-4o(50.7%) > SC-TSQL Full(50.3%) > DAIL-SQL(44.0%) > MAC-SQL(26.3%) — 는 또 하나의 보조 관측을 제공한다. *경량 래퍼 환경*에서 다중 에이전트 프롬프트 기법(MAC-SQL Selector 비활성 가능성, DAIL-SQL SC 호출 단순화)이 단순 Zero-shot 호출 대비 EX를 상회하지 못한 본 측정은, 원 알고리즘 강도의 평가가 아니라 *동일 백본·동일 평가 스크립트 조건의 상대 비교*에 한정된다(§6.4 한계 6). 본 관측은 §1.3 평가 인프라 항목의 *공정 비교 재실행 인프라(부분평가 한정)* 가치를 입증하면서, §6.2 운영 가이드라인의 핵심 메시지 — *NLI 검증을 교정 트리거가 아닌 진단 축으로 운영하라* — 를 보조적으로 지지한다.

**[평가 인프라]** 개인정보 제약 환경에서도 사전 검증이 가능한 **스키마-온리 평가 프로토콜**과, 동일 백본·BIRD 공식 평가 스크립트 기반의 **공정 비교 재실행 인프라**를 표준화했다. 한글 컬럼 설명 메타데이터 주입이 EX를 20→40%로 상승시킨 관측(파일럿)은 실무 DB의 명명 규약이 Text-to-SQL 품질에 주된 영향을 준다는 사실을 실증한다.

**[운영 가이드라인]** 가장 강조하고자 하는 본 연구의 결론은 §6.2의 **검증 축 운영 가이드라인 표**이다. 이는 "NLI는 EX를 안 올리니 무용하다" 또는 "NLI는 항상 교정 트리거이다" 같은 단순 결론을 회피하고, *SQL 신뢰도·실행 결과 상태·NLI 점수의 결합 조건*에 따른 단계별 운영 액션(자동 교정 / 사용자 경고 / HITL 트리거 / 결과 즉시 반환)을 정식화한다. 이 가이드라인은 GPT-4o급 백본을 사용하는 *실무 도입자가 즉시 채택 가능한 운영 정책*이며, 본 시연 시스템에 이미 내장되어 있다.

**의의의 종합.** 본 연구의 네 층 기여는 *상위 응용 목표 → 방법론 → 평가 인프라 → 운영 가이드라인*의 사슬로 연결되며, 각 층이 정량 근거(BIRD dev_300 어블레이션 4종 + 베이스라인 5종)와 정성 근거(시연 시스템·HRDB 사례 연구)에 의해 동시에 지지된다.

#### 6.5.1 한국 IT 서비스 산업에 대한 함의

본 연구는 한국 IT 서비스 산업이 *비전공자의 데이터 접근* 이라는 오랜 병목을 *별도 화면 개발 없이* 해소할 수 있음을 응용 사례로 입증하였다. 동시에 본 연구는 *완전 자동화의 환상* 을 경계한다 — 51% 수준의 EX는 자동 실행만으로는 운영 안전성을 확보하기 어려우며, **NLI 진단 축 + HITL 트리아지 + 사용자 경고** 의 결합이 필수적이다. 본 연구의 §6.2 운영 가이드라인 표는 한국 기업이 *오늘 즉시 채택 가능한 운영 정책* 으로 작성되었으며, 본 시연 시스템에 이미 내장되어 있다.

특히 한국형 인사 도메인에서 검증된 네 가지 특수성(영문 컬럼명 ↔ 한글 의미, 코드 ↔ 명칭 페어, 이력 테이블 시점, 시간 표현 cut-off)은 *공개 영어 벤치마크에는 거의 등장하지 않는* 한국 특유의 도전이며, 본 연구의 도메인 적응 설계는 다른 한국 기업 도메인(재무·운영·고객 관리 등)으로 즉시 일반화 가능한 *재사용 가능한 설계 자산* 으로 위치한다.

#### 6.5.2 학술적·실무적 의의의 종합

| 차원 | 본 연구의 기여 |
|---|---|
| **학술적 — 방법론** | NLI를 *교정 트리거*가 아닌 *독립 진단 축* 으로 운영하는 역할 분리, 그 진단 기여를 가시화하는 보조 관찰 지표(단독 탐지율) 도입 |
| **학술적 — 평가 표준** | 스키마-온리 평가 프로토콜 + 동일 백본 공정 비교 재실행 인프라 |
| **학술적 — 한국어 NLP** | 한국형 인사 도메인 네 가지 특수성의 정면 처리 — 영어 벤치마크에 가려진 한국 특수성 가시화 |
| **실무적 — 응용 가치** | 비전공자가 화면 개발 없이 SQL 접근 가능한 end-to-end 시스템 + 시연 시스템 |
| **실무적 — 운영 가이드라인** | 51% 정확도 환경에서도 안전한 운영을 가능케 하는 *증거 기반 결정 표* + 5단계 도입 절차 |
| **산업적 — ROI** | 자동 실행 only 대비 운영 위험 1/6 + 자동화 효율 85% 유지의 정량 분석 |

데이터 활용 수요가 폭증하는 한국 IT 서비스 산업 환경에서, 본 연구는 (i) 비전공자 데이터 접근의 기술적 가능성을 응용 시스템으로 입증하고, (ii) 그것을 *안전·정확하게 운영* 하기 위한 *증거 기반 의사결정 도구* 를 제공하며, (iii) 그 모든 결정의 정량 근거로 단독 탐지율 68.1%를 제시한다는 점에서 한국 IT 서비스 산업의 학술적·실무적 요구에 부합한다.

#### 6.5.3 연구의 핵심 메시지 요약

> **"NLI 의도 정합성 검증은 EX를 향상시키는 교정 도구로서의 기여가 본 표본에서 통계적으로 무의미하나, 약 50% 정확도 환경의 시스템을 *운영적으로 안전하게* 운용하기 위한 독립 진단 축의 후보로서의 가치는 보조 관찰 지표인 단독 탐지율 68.1%(BIRD dev_300, 외부 gold 기준)로 본 표본 규모에서 가시화된다. 본 연구는 이 비대칭을 한국 IT 서비스 산업이 검토 가능한 운영 가이드라인으로 정리하였다(통계적 일반화·도구 일반화 한계는 §6.4 한계 4·8·9·10·12)."**
